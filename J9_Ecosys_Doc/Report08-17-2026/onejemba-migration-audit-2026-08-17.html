OneJemba — As Actually Deployed Today

Findings

1 · Orphaned IAM role still authorized to send email as onejemba.com

Jemba9EcosystemComputeRole (created 2026-08-03, last used 2026-08-13) belonged to the old, now-deleted Amplify app. No Amplify app references it today — aws amplify list-apps in us-west-2 and us-east-2 shows only OneJemba. But the SES identity's resource policy for onejemba.com still explicitly grants this stale role ses:SendEmail / ses:SendRawEmail. It is a live, standing grant with no active application behind it. Recommend: delete the role (nothing depends on it) and update the SES identity policy to reference only OneJemba-Amplify-SSR-Compute, which currently has no SES permission of its own — a second, smaller gap, since the app itself cannot send mail directly today; only Cognito's own service-to-service call to SES works.

2 · Production (main / onejemba.com) is 16 commits behind dev and has no auth wired

Confirmed by direct branch comparison: local main and origin/main both sit at commit 46f5ca2 ("repo moves to us-west-2; P0 snapshot flag resolved") — essentially the seed commit. origin/dev is at 0b11a19, 16 commits ahead, containing the entire auth/Admin/App-Factory build. Live-verified on the Amplify branch config: the main branch has zero environment variables set, while dev has COGNITO_USER_POOL_ID, COGNITO_CLIENT_ID, and AMPLIFY_APP_ID. In its current state, onejemba.com serves only the placeholder page and cannot authenticate anyone. This is expected mid-build per CLAUDE.md's branch model ("promote to prod is one action: merge dev into main") — flagging only so nobody is surprised visiting the live URL today.

3 · Apex domain (onejemba.com) not yet verified in Amplify's own records

Amplify's domain association for onejemba.com shows the main-branch apex subdomain setting as "verified": false, while www and dev are both "verified": true. In practice, a direct request to https://onejemba.com during this audit returned HTTP 200 — so it may simply be that Amplify's status hasn't caught up with DNS propagation. Worth a manual recheck in the Amplify console before treating the bare domain as production-ready.

4 · BoardLab and Dataroom have no place in the new plan

Every phase of the Build Order (P0–P5) is documented in OneJemba's own docs/workplan/ and CLAUDE.md. Only OKR is named for extraction and eventual integration (P5, via the App Factory). Neither BoardLab nor Dataroom appears anywhere in the new repo, its house rules, or its workplan. Their source code and full commit history currently exist only in your local clone of the deleted Jemba9_Ecosystem repo (see Finding 5) — there is no stated plan to bring either forward into OneJemba. If both are still wanted, this needs a decision and a P-phase of their own; if BoardLab in particular (which had a working, tested Next.js app with Lakebase and Databricks AI Gateway integration per the 2026-08-14 audit) is meant to be revived, it should happen before this local clone is the only surviving copy of its history.

5 · The P0 archive bundle was not found on this machine

OneJemba's own migration plan (docs/workplan/prompts/CC1_extract_and_archive.md) calls the pre-deletion archive "the only history that survives — treat it as the deliverable it is," to be written to ~/Documents/Claude/Projects/OneJemba/migration/ with a recorded SHA256. That directory does not exist on this machine — ~/Documents/Claude/Projects/ is absent entirely. This strongly suggests your partner ran P0 on their own machine and only pushed the resulting OneJemba git repo (which is gitignore-excluded from carrying the archive) to CodeCommit. You are not currently able to verify the archive bundle exists, its SHA256, or that it is backed up anywhere durable. The good news: your own local clone of the old repo (/Users/michaelberry/Documents/Jemba9/CasecadeProjects/Jemba9_Ecosystem, 109 commits, all 5 known branches present including okr-app and feat/board-lab) is itself a substantially complete independent copy — but it is a single laptop's disk, which is exactly the failure mode the archive step exists to avoid. Recommend: ask your partner directly whether the bundle exists and where, and separately back up this local clone (e.g. git bundle create to cloud storage) as a second point of safety regardless.

6 · Carried over, unresolved since the 2026-08-14 audit: plaintext BoardLab credentials on disk

The prior audit flagged Applications/boardlab/.env as containing four live plaintext credentials (three Lakebase role passwords plus a Databricks client secret) and recommended rotation. That file is still present, unrotated, gitignored in your local Jemba9_Ecosystem clone today. It was never committed to git (confirmed — no .env appears anywhere in the repo's full commit history across all branches), so this is a local-disk exposure, not a repo leak. Since BoardLab is not part of the OneJemba plan (Finding 4), these credentials are now for infrastructure that may no longer be reachable — worth confirming whether they still grant real access, and rotating or deleting them either way.

7 · The account-confusion question from the prior audit is now resolved

2026-08-14's audit asked, as its top open question: "which account is the real deploy target — 573631993254 or 824999955649?" OneJemba's CLAUDE.md (House Rule R1) answers this decisively and for a reason not previously documented: 573631993254 is "Cloud Cowboy" — a different company entirely, not a legacy or alternate Jemba9 environment. Every prior reference to it in the old repo's docs and Dataroom's inherited GitHub Actions workflows was, per this new framing, simply wrong. 824999955649 is confirmed as the one true account going forward. One residual risk this creates: this machine's default (unqualified) AWS profile still points at Cloud Cowboy per CLAUDE.md's own warning — any stray aws command run without an explicit --profile risks operating against a different company's AWS account. This audit used the explicit jemba9-dev profile throughout for exactly this reason.

Minimum Acceptance Test — The First Day It Counts as "Running"

The environment should not be declared fully operational merely because Amplify says SUCCEED. Before calling dev ready, execute and record this golden path:

  1. A bootstrap owner requests and verifies an email OTP through dev.onejemba.com, reaches the launcher, and sees Admin.
  2. The owner creates/invites a normal test user, assigns app:okr, and verifies the user sees OKR but does not see or reach Admin.
  3. That user creates, updates, and reads one non-sensitive test OKR; the record lands in the okr schema, with the app unable to write platform or another app's schema.
  4. The owner revokes app:okr; after a token refresh, the user loses both the launcher tile and direct-route access.
  5. A deploy from dev is observed end-to-end in Amplify, then a known-safe redeploy is demonstrated so the team has a practical recovery path.
  6. The result, schema migration version, build id, test users/groups, and rollback/redeploy method are captured in a short dev runbook. Only then is a reviewed promotion to main meaningful.
