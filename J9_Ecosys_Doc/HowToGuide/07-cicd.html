7.1 — The pipeline

What already exists: .github/workflows/ci.yml at the repo root, which runs typecheck, lint, format check, unit tests, a build, and an integration suite against a Postgres service container. It is solid and you should not touch it. What is missing is everything after the green check.

Delete these two files first

Applications/dataroom/.github/workflows/deploy.yml and deploy-staging.yml both contain:

AWS_ROLE_ARN: arn:aws:iam::573631993254:role/CloudCowboyWebDeploy
S3_BUCKET: cloudcowboy-us-prod-site
CLOUDFRONT_DISTRIBUTION_ID: E17S88TQPA7PM1

They deploy a static Vite bundle — which this app no longer produces — to another company's account, and they inject VITE_SUPABASE_* variables the app no longer reads. They are dead code pointed at the wrong target. Delete both, along with the empty .github directory under Applications/dataroom/.

Note also that workflows nested in a subdirectory do not run on GitHub — only .github/workflows/ at the repository root does — so they are currently inert. That is luck, not design. Remove them before someone restructures the repo.

7.2 — The deploy roles

Two roles: one that can only touch dev, one that can only touch prod. The dev role trusts pushes to main; the prod role trusts a GitHub environment, which is what gives you the approval gate.

Ecosystem/infra/terraform/50-compute/iam-deploy.tf

variable "github_repo" {
  description = "owner/repo, e.g. jemba9/Jemba9_Ecosystem"
  type        = string
}

data "aws_iam_policy_document" "gha_assume" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [data.terraform_remote_state.bootstrap.outputs.github_oidc_provider_arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    # This is the whole security boundary. Get the subject wrong — a bare
    # `repo:owner/repo:*` — and any branch in the repo, including one opened by a
    # fork's pull request, can assume the role.
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:sub"
      values = local.is_prod ? [
        "repo:${var.github_repo}:environment:prod",
      ] : [
        "repo:${var.github_repo}:ref:refs/heads/main",
        "repo:${var.github_repo}:environment:dev",
      ]
    }
  }
}

resource "aws_iam_role" "deploy" {
  name               = "${local.prefix}-deploy"
  description        = "Assumed by GitHub Actions to deploy the ${local.env} environment."
  assume_role_policy = data.aws_iam_policy_document.gha_assume.json
  max_session_duration = 3600
}

data "aws_iam_policy_document" "deploy" {
  # --- ECR: push images. Repositories are shared, so this is not env-scoped.
  statement {
    actions   = ["ecr:GetAuthorizationToken"]
    resources = ["*"]
  }

  statement {
    actions = [
      "ecr:BatchCheckLayerAvailability",
      "ecr:CompleteLayerUpload",
      "ecr:InitiateLayerUpload",
      "ecr:PutImage",
      "ecr:UploadLayerPart",
      "ecr:BatchGetImage",
      "ecr:GetDownloadUrlForLayer",
      "ecr:DescribeImages",
    ]
    resources = [
      "arn:aws:ecr:${var.region}:824999955649:repository/j9/platform",
      "arn:aws:ecr:${var.region}:824999955649:repository/j9/okr",
      "arn:aws:ecr:${var.region}:824999955649:repository/j9/dataroom",
    ]
  }

  # --- ECS: register task definitions and update this environment's services only.
  statement {
    actions   = ["ecs:RegisterTaskDefinition", "ecs:DescribeTaskDefinition"]
    resources = ["*"]      # this API does not support resource-level permissions
  }

  statement {
    actions = [
      "ecs:UpdateService",
      "ecs:DescribeServices",
      "ecs:RunTask",
      "ecs:DescribeTasks",
      "ecs:ListTasks",
      "ecs:StopTask",
    ]
    resources = [
      "arn:aws:ecs:${var.region}:824999955649:service/${local.prefix}-cluster/*",
      "arn:aws:ecs:${var.region}:824999955649:task/${local.prefix}-cluster/*",
      "arn:aws:ecs:${var.region}:824999955649:task-definition/${local.prefix}-*:*",
    ]
  }

  # --- Pass only this environment's task roles into a task definition.
  statement {
    actions = ["iam:PassRole"]
    resources = [
      "arn:aws:iam::824999955649:role/${local.prefix}-*-exec",
      "arn:aws:iam::824999955649:role/${local.prefix}-*-task",
    ]
    condition {
      test     = "StringEquals"
      variable = "iam:PassedToService"
      values   = ["ecs-tasks.amazonaws.com"]
    }
  }

  # --- Read logs from the migration task so the workflow can print them.
  statement {
    actions   = ["logs:GetLogEvents", "logs:DescribeLogStreams"]
    resources = ["arn:aws:logs:${var.region}:824999955649:log-group:/j9/${local.env}/*"]
  }

  # --- Invalidate the CDN after a deploy.
  statement {
    actions   = ["cloudfront:CreateInvalidation", "cloudfront:GetInvalidation"]
    resources = ["arn:aws:cloudfront::824999955649:distribution/*"]
  }
}

resource "aws_iam_role_policy" "deploy" {
  name   = "deploy"
  role   = aws_iam_role.deploy.id
  policy = data.aws_iam_policy_document.deploy.json
}
The sub condition is the whole boundary

iam:PassRole scoped to ${local.prefix}-* is what stops the dev deploy role from launching a task with the prod task role — which would give it the prod SSM parameters. Combined with the sub condition on the trust policy, a compromised pull request from a fork gets nothing: it cannot assume either role, because a fork's token subject is neither refs/heads/main nor a protected environment.

Never write values = ["repo:owner/repo:*"]. It is the single most common OIDC misconfiguration and it is equivalent to publishing an access key.

7.3 — The deploy workflow

One workflow, three services, driven by a matrix. It only builds what changed, so an OKR-only commit does not redeploy the platform.

.github/workflows/deploy.yml

name: Deploy

on:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      services:
        description: 'Comma-separated services to force-deploy (platform,okr,dataroom)'
        required: false
        default: ''

concurrency:
  group: deploy-dev
  cancel-in-progress: false      # queue deploys; never cancel one mid-flight

permissions:
  id-token: write                # required for OIDC
  contents: read

env:
  AWS_REGION: us-west-2
  AWS_ACCOUNT: "824999955649"
  ENVIRONMENT: dev
  CLUSTER: j9-dev-cluster

jobs:
  # ------------------------------------------------------------------ changes
  changes:
    runs-on: ubuntu-latest
    outputs:
      platform: ${{ steps.filter.outputs.platform }}
      okr:      ${{ steps.filter.outputs.okr }}
      dataroom: ${{ steps.filter.outputs.dataroom }}
    steps:
      - uses: actions/checkout@v4
      - uses: dorny/paths-filter@v3
        id: filter
        with:
          filters: |
            platform:
              - 'Ecosystem/**'
            okr:
              - 'Applications/OKR/**'
            dataroom:
              - 'Applications/dataroom/**'

  # -------------------------------------------------------------------- build
  build:
    needs: changes
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          - service: platform
            path: Ecosystem
            changed: ${{ needs.changes.outputs.platform }}
          - service: okr
            path: Applications/OKR
            changed: ${{ needs.changes.outputs.okr }}
          - service: dataroom
            path: Applications/dataroom
            changed: ${{ needs.changes.outputs.dataroom }}

    steps:
      - name: Skip unchanged
        if: matrix.changed != 'true' && github.event_name == 'push'
        run: echo "No changes in ${{ matrix.path }} — skipping." && exit 0

      - uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ env.AWS_ACCOUNT }}:role/j9-${{ env.ENVIRONMENT }}-deploy
          aws-region: ${{ env.AWS_REGION }}
          role-session-name: gha-${{ matrix.service }}-${{ github.run_id }}

      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr

      - uses: docker/setup-buildx-action@v3

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: ${{ matrix.path }}
          file: ${{ matrix.path }}/Dockerfile
          platforms: linux/arm64          # matches the Graviton task definitions
          push: true
          tags: ${{ steps.ecr.outputs.registry }}/j9/${{ matrix.service }}:${{ github.sha }}
          cache-from: type=gha,scope=${{ matrix.service }}
          cache-to: type=gha,mode=max,scope=${{ matrix.service }}
          build-args: |
            NEXT_PUBLIC_PLATFORM_PORTAL_URL=${{ vars.FRONT_DOOR_URL }}

  # ---------------------------------------------------------------- migrate
  # Runs before the services roll, as a one-off task using the OWNER credential.
  # Prisma migrations are additive and forward-only, so this ordering is safe.
  migrate:
    needs: [changes, build]
    runs-on: ubuntu-latest
    strategy:
      max-parallel: 1               # never two migrations at once
      matrix:
        include:
          - service: platform
            changed: ${{ needs.changes.outputs.platform }}
            command: '["npx","prisma","migrate","deploy"]'
          - service: okr
            changed: ${{ needs.changes.outputs.okr }}
            command: '["npx","prisma","migrate","deploy"]'
          - service: dataroom
            changed: ${{ needs.changes.outputs.dataroom }}
            command: '["node","scripts/db-migrate.mjs"]'

    steps:
      - name: Skip unchanged
        if: matrix.changed != 'true' && github.event_name == 'push'
        run: echo "skip" && exit 0

      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ env.AWS_ACCOUNT }}:role/j9-${{ env.ENVIRONMENT }}-deploy
          aws-region: ${{ env.AWS_REGION }}

      - name: Run the migration task and wait
        run: |
          set -euo pipefail

          TASK_ARN=$(aws ecs run-task \
            --cluster "$CLUSTER" \
            --task-definition "j9-${ENVIRONMENT}-${{ matrix.service }}-migrate" \
            --launch-type FARGATE \
            --network-configuration "awsvpcConfiguration={subnets=[${{ vars.PRIVATE_SUBNETS }}],securityGroups=[${{ vars.TASK_SG }}],assignPublicIp=DISABLED}" \
            --overrides "{\"containerOverrides\":[{\"name\":\"migrate\",\"command\":${{ matrix.command }},\"environment\":[{\"name\":\"IMAGE_SHA\",\"value\":\"$GITHUB_SHA\"}]}]}" \
            --query 'tasks[0].taskArn' --output text)

          echo "task: $TASK_ARN"
          aws ecs wait tasks-stopped --cluster "$CLUSTER" --tasks "$TASK_ARN"

          EXIT=$(aws ecs describe-tasks --cluster "$CLUSTER" --tasks "$TASK_ARN" \
                 --query 'tasks[0].containers[0].exitCode' --output text)

          # Print the logs whether it worked or not — a failed migration with no
          # visible output is the worst possible pipeline outcome.
          TASK_ID=${TASK_ARN##*/}
          aws logs get-log-events \
            --log-group-name "/j9/${ENVIRONMENT}/${{ matrix.service }}" \
            --log-stream-name "migrate/migrate/$TASK_ID" \
            --query 'events[].message' --output text || true

          if [ "$EXIT" != "0" ]; then
            echo "::error::Migration for ${{ matrix.service }} exited $EXIT"
            exit 1
          fi

  # ----------------------------------------------------------------- deploy
  deploy:
    needs: [changes, build, migrate]
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        include:
          - service: platform
            changed: ${{ needs.changes.outputs.platform }}
          - service: worker
            changed: ${{ needs.changes.outputs.platform }}   # same image
          - service: okr
            changed: ${{ needs.changes.outputs.okr }}
          - service: dataroom
            changed: ${{ needs.changes.outputs.dataroom }}

    steps:
      - name: Skip unchanged
        if: matrix.changed != 'true' && github.event_name == 'push'
        run: echo "skip" && exit 0

      - uses: actions/checkout@v4

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::${{ env.AWS_ACCOUNT }}:role/j9-${{ env.ENVIRONMENT }}-deploy
          aws-region: ${{ env.AWS_REGION }}

      - name: Render the new task definition
        id: taskdef
        run: |
          IMAGE_SERVICE=${{ matrix.service }}
          [ "$IMAGE_SERVICE" = "worker" ] && IMAGE_SERVICE=platform

          aws ecs describe-task-definition \
            --task-definition "j9-${ENVIRONMENT}-${{ matrix.service }}" \
            --query taskDefinition > taskdef.json

          jq --arg img "${{ env.AWS_ACCOUNT }}.dkr.ecr.${{ env.AWS_REGION }}.amazonaws.com/j9/$IMAGE_SERVICE:$GITHUB_SHA" \
             'del(.taskDefinitionArn,.revision,.status,.requiresAttributes,
                  .compatibilities,.registeredAt,.registeredBy)
              | .containerDefinitions[0].image = $img' \
             taskdef.json > new-taskdef.json

          ARN=$(aws ecs register-task-definition \
                --cli-input-json file://new-taskdef.json \
                --query 'taskDefinition.taskDefinitionArn' --output text)
          echo "arn=$ARN" >> "$GITHUB_OUTPUT"

      - name: Update the service and wait for stability
        run: |
          aws ecs update-service \
            --cluster "$CLUSTER" \
            --service "j9-${ENVIRONMENT}-${{ matrix.service }}" \
            --task-definition "${{ steps.taskdef.outputs.arn }}" \
            --query 'service.serviceName' --output text

          # The deployment circuit breaker rolls back on failure; this wait is how
          # the workflow finds out that happened.
          aws ecs wait services-stable \
            --cluster "$CLUSTER" \
            --services "j9-${ENVIRONMENT}-${{ matrix.service }}"

  # ------------------------------------------------------------------ smoke
  smoke:
    needs: deploy
    if: always() && needs.deploy.result == 'success'
    runs-on: ubuntu-latest
    steps:
      - name: Health checks through the front door
        run: |
          set -euo pipefail
          BASE="${{ vars.FRONT_DOOR_URL }}"
          fail=0
          for p in /healthz /okr/healthz /dataroom/healthz; do
            code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 15 "$BASE$p")
            echo "$p -> $code"
            [ "$code" = "200" ] || fail=1
          done

          # HSTS is set by next.config.ts; if it is missing we are seeing an
          # error page rather than the app.
          curl -sI "$BASE/healthz" | grep -qi strict-transport-security \
            || { echo "::error::No HSTS header — not reaching the app"; fail=1; }

          exit $fail

The migration task definitions

Three small task definitions, one per app, that exist only to be run once and stop. They differ from the service definitions in exactly two ways: they get the owner connection string, and they have no port mapping or health check.

Ecosystem/infra/terraform/50-compute/task-migrate.tf

locals {
  migrate = {
    platform = { repo = "platform", db_scope = "platform" }
    okr      = { repo = "okr",      db_scope = "okr" }
    dataroom = { repo = "dataroom", db_scope = "dataroom" }
  }
}

# A dedicated role, because this is the only thing in the system allowed to read
# the owner credentials.
resource "aws_iam_role" "migrate_exec" {
  for_each           = local.migrate
  name               = "${local.prefix}-${each.key}-migrate-exec"
  assume_role_policy = data.aws_iam_policy_document.ecs_assume.json
}

resource "aws_iam_role_policy_attachment" "migrate_exec_managed" {
  for_each   = aws_iam_role.migrate_exec
  role       = each.value.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}

resource "aws_iam_role_policy" "migrate_exec_secrets" {
  for_each = local.migrate
  name     = "read-owner-credential"
  role     = aws_iam_role.migrate_exec[each.key].id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect   = "Allow"
        Action   = ["ssm:GetParameters", "ssm:GetParameter"]
        Resource = "arn:aws:ssm:${var.region}:824999955649:parameter/j9/${local.env}/${each.value.db_scope}/DATABASE_URL"
      },
      {
        Effect   = "Allow"
        Action   = ["kms:Decrypt"]
        Resource = data.terraform_remote_state.secrets.outputs.kms_key_arn
      },
    ]
  })
}

resource "aws_ecs_task_definition" "migrate" {
  for_each                 = local.migrate
  family                   = "${local.prefix}-${each.key}-migrate"
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc"
  cpu                      = 512
  memory                   = 1024
  execution_role_arn       = aws_iam_role.migrate_exec[each.key].arn
  task_role_arn            = aws_iam_role.migrate_exec[each.key].arn

  runtime_platform {
    operating_system_family = "LINUX"
    cpu_architecture        = "ARM64"
  }

  container_definitions = jsonencode([{
    name      = "migrate"
    image     = "824999955649.dkr.ecr.${var.region}.amazonaws.com/j9/${each.value.repo}:latest"
    essential = true
    # The command is always supplied as an override by the workflow.
    command   = ["true"]

    secrets = [
      { name = "DATABASE_URL", valueFrom = "${local.ssm}/${each.value.db_scope}/DATABASE_URL" },
    ]

    logConfiguration = {
      logDriver = "awslogs"
      options = {
        "awslogs-group"         = aws_cloudwatch_log_group.service[each.key].name
        "awslogs-region"        = var.region
        "awslogs-stream-prefix" = "migrate"
      }
    }
  }])
}
The image tag on the migration task

The task definition above pins :latest, which is wrong for the same reason immutable tags are right. The workflow should override the image, not just the command — but ecs run-task container overrides cannot change the image. The clean fix is for the workflow to register a fresh revision of the migration task definition with the correct SHA before running it, exactly as the deploy job does for the services. Add that step; the version above is deliberately left simple so the shape is legible.

7.4 — Promotion to prod

Prod never builds. It re-tags a digest that already ran in dev and rolls the services onto it.

.github/workflows/promote.yml

name: Promote to prod

on:
  workflow_dispatch:
    inputs:
      sha:
        description: 'The commit SHA already deployed and verified in dev'
        required: true
      services:
        description: 'platform, okr, dataroom, or all'
        required: true
        default: all

concurrency:
  group: deploy-prod
  cancel-in-progress: false

permissions:
  id-token: write
  contents: read

jobs:
  promote:
    runs-on: ubuntu-latest
    # This is the approval gate. Configure required reviewers on the `prod`
    # environment in GitHub settings; the job pauses until someone approves.
    environment: prod

    env:
      AWS_REGION: us-west-2
      AWS_ACCOUNT: "824999955649"
      CLUSTER: j9-prod-cluster

    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ inputs.sha }}

      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::824999955649:role/j9-prod-deploy
          aws-region: us-west-2

      - name: Verify the image exists and record its digest
        run: |
          set -euo pipefail
          for svc in platform okr dataroom; do
            case "${{ inputs.services }}" in all|*"$svc"*) ;; *) continue ;; esac
            DIGEST=$(aws ecr describe-images \
              --repository-name "j9/$svc" \
              --image-ids imageTag=${{ inputs.sha }} \
              --query 'imageDetails[0].imageDigest' --output text)
            echo "$svc -> $DIGEST"
            # If this fails, the SHA was never built — which means it was never
            # in dev, which means it must not go to prod.
          done

      - name: Roll the prod services
        run: |
          set -euo pipefail
          for svc in platform worker okr dataroom; do
            IMG=$svc; [ "$svc" = "worker" ] && IMG=platform
            case "${{ inputs.services }}" in
              all) ;;
              *"$IMG"*) ;;
              *) continue ;;
            esac

            aws ecs describe-task-definition --task-definition "j9-prod-$svc" \
              --query taskDefinition > td.json

            jq --arg img "824999955649.dkr.ecr.us-west-2.amazonaws.com/j9/$IMG:${{ inputs.sha }}" \
               'del(.taskDefinitionArn,.revision,.status,.requiresAttributes,
                    .compatibilities,.registeredAt,.registeredBy)
                | .containerDefinitions[0].image = $img' td.json > new.json

            ARN=$(aws ecs register-task-definition --cli-input-json file://new.json \
                  --query 'taskDefinition.taskDefinitionArn' --output text)

            aws ecs update-service --cluster "$CLUSTER" --service "j9-prod-$svc" \
              --task-definition "$ARN" --query 'service.serviceName' --output text
          done

          aws ecs wait services-stable --cluster "$CLUSTER" \
            --services j9-prod-platform j9-prod-worker j9-prod-okr j9-prod-dataroom

      - name: Smoke test
        run: |
          for p in /healthz /okr/healthz /dataroom/healthz; do
            code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 15 "https://jemba9.com$p")
            echo "$p -> $code"
            [ "$code" = "200" ]
          done
Prod migrations are not in this workflow, on purpose

A schema change against production data is a decision, not a step. Run it deliberately, as its own ecs run-task, after reading the migration SQL, with a fresh snapshot taken first:

aws rds create-db-snapshot --db-instance-identifier j9-prod-pg \
  --db-snapshot-identifier "j9-prod-pre-$(date +%Y%m%d%H%M)"

Then run the migration task, then promote the image. Two of the platform's migrations install append-only triggers and RLS policies on the audit and event tables; a partial application of that is not something you want to discover from a dashboard.

7.5 — GitHub configuration

No secrets are needed for AWS — that is the point of OIDC. What you do need is a handful of variables, plus two environments.

WhereNameValue
Repository variablesFRONT_DOOR_URL the dev CloudFront URL, or https://dev.jemba9.com
Repository variablesPRIVATE_SUBNETS subnet-aaa,subnet-bbb from the network layer output
Repository variablesTASK_SGsg-xxxx
Environment dev— no reviewers; exists so the OIDC subject can reference it
Environment prodrequired reviewers at least one person who is not the author; optionally a wait timer
Branch protection on main— require the CI workflow to pass; require a pull request
Verify the trust boundary before you trust it

Open a pull request from a branch (not main) that adds a step calling configure-aws-credentials with the dev role. It must fail with Not authorized to perform sts:AssumeRoleWithWebIdentity.

If it succeeds, your sub condition is too broad and any contributor can deploy. Fix it before you put a real secret in SSM.
