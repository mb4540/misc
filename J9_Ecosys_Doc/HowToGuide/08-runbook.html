8.1 — Local development first

Before you touch AWS, get the three projects running locally. It takes an hour and it means that when something fails in AWS you know whether it is your infrastructure or the application.

Each project brings its own Postgres on a deliberately different host port, so all three can run at once:

ProjectPostgresRedisAppURL
Ecosystem/543363803000 http://localhost:3000
Applications/OKR/543663823001 http://localhost:3001/okr
Applications/dataroom/5435—8080 http://localhost:8080/dataroom
# ---- the platform
cd Ecosystem
cp .env.example .env
cp .env.example .env.local          # Prisma CLI reads .env; Next reads .env.local
npm install
docker compose up -d                # Postgres 16 on 5433, Redis 7 on 6380
npx prisma migrate deploy
npm run seed                        # idempotent; reads company.config.yaml
npm run dev                         # http://localhost:3000  — AUTH_PROVIDER=mock

# In a second shell, the worker:
npm run worker

# ---- OKR
cd ../Applications/OKR
npm install
npm run db:up                       # docker-compose.dev.yml — 5436 / 6382
npm run db:migrate
npm run dev                         # http://localhost:3001/okr

# ---- Data Room
cd ../dataroom
cp .env.example .env
npm install
docker compose up -d                # dataroom-postgres on 5435
npm run db:migrate                  # applies db/migrations/*.sql as the owner
npm run dev                         # http://localhost:8080/dataroom
Locally the apps use a mock identity, not Cognito

The platform runs with AUTH_PROVIDER=mock against a local OIDC issuer with real crypto and no cloud. The Data Room additionally supports J9_DEV_MOCK=1 with J9_DEV_MOCK_ROLE=investor|admin so it works before an API key exists.

Both are correct locally and both must be absent in AWS. The switch to Cognito is environment values only — per infra/terraform/README.md, "no app code changes are needed to switch from mock to Cognito".

Confirm the platform works before moving on:

cd Ecosystem
npm test                     # unit, no database
npm run typecheck
npm run test:integration     # append-only triggers, one-active-grant, RLS isolation, seed idempotency

The integration suite is the one worth running, because it exercises the exact database behaviour — RLS under the j9_app role, append-only triggers — that your AWS role setup has to reproduce.

8.2 — The bootstrap, in order

  1. Confirm the account. aws sts get-caller-identity --profile j9 must print 824999955649. Everything after this is wasted if it does not.
  2. Guardrails. S3 account-wide public access block, EBS default encryption in both regions, CloudTrail, GuardDuty, cost allocation tags. Chapter 2.5.
  3. Bootstrap layer. 00-bootstrap: state bucket, lock table, GitHub OIDC provider, budgets. Then migrate its own state into the bucket. Chapter 2.6.
  4. Generate the six database passwords into a gitignored shared/dev.secret.tfvars. Chapter 4.2.
  5. Network (dev workspace). VPC, subnets, NAT, security groups, VPC endpoints. Verify: three route tables exist and the isolated one has no 0.0.0.0/0 route. 
    aws ec2 describe-route-tables \
  --filters "Name=tag:Name,Values=j9-dev-rt-isolated" \
  --query 'RouteTables[0].Routes[].DestinationCidrBlock'
  6. Secrets layer, first pass. The KMS key only — the parameters depend on the database endpoint, which does not exist yet. Target it: 
    terraform apply -target=aws_kms_key.main -target=aws_kms_alias.main \
  -target=aws_kms_key_policy.main -var-file=../shared/dev.tfvars
  7. Data. RDS, ElastiCache, S3. This is the slow one — 10 to 15 minutes for the database.
  8. Database bootstrap SQL. Create the three databases and six roles, then the Data Room's schema and grants. Chapter 3.6. Verify rolbypassrls = f on all three _app roles before proceeding.
  9. Identity, first pass. Cognito with front_door_url = "", so callbacks point at localhost. You will apply this layer again in step 15.
  10. Secrets layer, full apply. All the SSM parameters now that the database, Redis, and Cognito endpoints exist. The three placeholder parameters get PLACEHOLDER-REPLACE-ME.
  11. Build and push the first images. Locally, before CI exists, so you are not debugging two things at once: 
    aws ecr get-login-password --region us-west-2 \
  | docker login --username AWS --password-stdin 824999955649.dkr.ecr.us-west-2.amazonaws.com

for s in platform:Ecosystem okr:Applications/OKR dataroom:Applications/dataroom; do
  name=${s%%:*}; path=${s#*:}
  docker buildx build --platform linux/arm64 --push \
    -t "824999955649.dkr.ecr.us-west-2.amazonaws.com/j9/$name:bootstrap" \
    "$path"
done
  12. Compute. ECR (created here on the dev apply), cluster, log groups, task definitions, the two ALBs, target groups, listener rules, services. Set the image tag variables to bootstrap.
  13. Verify compute without the CDN. Chapter 5.8. Do not continue until all three target groups are healthy. This is where the base-path health check and the task-to-task security group rule prove themselves.
  14. Front door. ACM (skipped when domain_name = ""), WAF in count mode, CloudFront. Capture the distribution domain name.
  15. Identity, second pass, and compute again. Re-apply both with front_door_url=https://<the CloudFront domain> so the Cognito callbacks and PLATFORM_SELF_URL are correct. Chapter 6.5.
  16. Migrate and seed the platform. Run the migration task, then the seed. The seed creates the internal org, the reserved platform app, and the Admin app with its permissions and system roles.
  17. Bootstrap the first Org Admin and sign in through the CloudFront URL. This is the moment the whole thing becomes real.
  18. Register the two app manifests in Admin → Apps (Preview, then Apply), issue an API key for each, write both into SSM, and force a new deployment of the two app services. Chapter 4.4.
  19. Acceptance test. The one the App Contract actually specifies: log in → open the app → perform a gated action → revoke the grant in Admin → the same action is denied on the next request. If that passes, the enforcement-point design is working end to end.
  20. Wire CI/CD and confirm a push to main deploys dev. Chapter 7.
  21. Repeat 5 through 16 in the prod workspace with prod.tfvars. It is the same commands. Do not migrate or seed prod until someone has decided what data goes in it.

8.3 — One script that tells you whether an environment is well

Ecosystem/scripts/verify-env.sh

#!/usr/bin/env bash
# Usage: ./verify-env.sh dev https://dxxxxxxxxxxxxx.cloudfront.net
set -uo pipefail

ENV="${1:?environment}"
BASE="${2:?front door url}"
CLUSTER="j9-${ENV}-cluster"
fail=0

ok()   { printf '  \033[32mok\033[0m   %s\n' "$1"; }
bad()  { printf '  \033[31mFAIL\033[0m %s\n' "$1"; fail=1; }

echo "== account"
acct=$(aws sts get-caller-identity --query Account --output text)
[ "$acct" = "824999955649" ] && ok "account $acct" || bad "wrong account: $acct"

echo "== services"
for svc in platform worker okr dataroom; do
  read -r running desired < <(aws ecs describe-services \
    --cluster "$CLUSTER" --services "j9-${ENV}-${svc}" \
    --query 'services[0].[runningCount,desiredCount]' --output text)
  [ "$running" = "$desired" ] && [ "$running" != "0" ] \
    && ok "$svc $running/$desired" || bad "$svc $running/$desired"
done

echo "== target groups"
for tg in platform okr dataroom; do
  arn=$(aws elbv2 describe-target-groups --names "j9-${ENV}-${tg}-tg" \
        --query 'TargetGroups[0].TargetGroupArn' --output text 2>/dev/null)
  states=$(aws elbv2 describe-target-health --target-group-arn "$arn" \
           --query 'TargetHealthDescriptions[].TargetHealth.State' --output text)
  case "$states" in
    *unhealthy*|"") bad "$tg: $states" ;;
    *)              ok  "$tg: $states" ;;
  esac
done

echo "== health endpoints"
for p in /healthz /okr/healthz /dataroom/healthz; do
  code=$(curl -s -o /dev/null -w '%{http_code}' --max-time 15 "$BASE$p")
  [ "$code" = "200" ] && ok "$p $code" || bad "$p $code"
done

echo "== security headers"
hdrs=$(curl -sI --max-time 15 "$BASE/healthz")
for h in strict-transport-security content-security-policy x-frame-options x-content-type-options; do
  grep -qi "^$h" <<<"$hdrs" && ok "$h" || bad "$h missing"
done

echo "== direct ALB access is refused"
alb=$(aws elbv2 describe-load-balancers --names "j9-${ENV}-alb" \
      --query 'LoadBalancers[0].DNSName' --output text)
code=$(curl -sk -o /dev/null -w '%{http_code}' --max-time 10 "https://$alb/healthz" || echo 000)
[ "$code" = "403" ] || [ "$code" = "000" ] && ok "direct ALB -> $code" || bad "direct ALB -> $code"

echo "== no mock identity in any task definition"
for svc in platform worker okr dataroom; do
  if aws ecs describe-task-definition --task-definition "j9-${ENV}-${svc}" \
     --query 'taskDefinition.containerDefinitions[].environment[].name' --output text \
     | grep -qE 'J9_DEV_MOCK|AUTH_PROVIDER_MOCK'; then
    bad "$svc has a mock identity variable"
  else
    ok "$svc clean"
  fi
done

echo "== database roles cannot bypass RLS"
echo "  (run manually — the database is not reachable from here by design)"
echo "  SELECT rolname, rolsuper, rolbypassrls FROM pg_roles"
echo "   WHERE rolname LIKE '%_app';   -- all must be f, f"

exit $fail

8.4 — What it costs

Order-of-magnitude monthly figures for us-west-2, at low traffic. Verify against the AWS pricing calculator before quoting them to anyone — prices change and this table will age.

ItemdevprodNote
NAT gateway~33~66one, then one per AZ. Plus data processing.
ALB (public + internal)~35~40two load balancers, plus LCU charges
Fargate — 4 services~35~180 dev on Spot at 0.5 vCPU; prod on-demand, 2 tasks each at 1 vCPU
RDS PostgreSQL~15~130t4g.micro single-AZ vs t4g.medium Multi-AZ, plus storage and backups
ElastiCache Redis~12~50one t4g.micro vs two t4g.small
VPC interface endpoints~35~70five endpoints, per AZ. Trades against NAT data charges.
CloudFront~2~15traffic-dependent; low at this scale
WAF~8~12web ACL plus rules plus requests
KMS, SSM, Secrets Manager~3~5one key, standard-tier parameters
CloudWatch logs and metrics~8~35 prod has enhanced Container Insights and 365-day retention
S3, ECR, CloudTrail, GuardDuty~10~20—
Total~195~625the budgets in chapter 2.5 are set to 250 and 900

If that dev number is uncomfortable, the three levers in order of payoff are: drop the interface endpoints and accept NAT data charges (saves ~35), collapse the internal ALB by using service discovery instead (saves ~18), and scale dev services to zero outside working hours with a scheduled autoscaling action (saves ~20). Do not economise on the RDS backups or the audit log retention — those are policy, not infrastructure preference.

8.5 — Troubleshooting

SymptomAlmost alwaysFix
Targets cycle healthy then unhealthy forever; logs show "ready in 400ms" Health check path missing the base path, or HOSTNAME not set to 0.0.0.0 Target group path must be /okr/healthz and /dataroom/healthz. Confirm HOSTNAME is in the task definition and the Dockerfile.
UI loads, every action denied, no errors anywhere App tasks cannot reach the platform The self = true rule on the task security group (3.2), and J9_PLATFORM_URL pointing at the internal ALB.
Every user sees every org's data The app is connecting as the owner role, or an _app role has BYPASSRLS Check which parameter the task reads — it must be APP_DATABASE_URL. Then check pg_roles. This is a data-exposure bug; treat it as an incident.
Task stops immediately, ResourceInitializationError mentioning SSM The execution role cannot read a parameter, or cannot decrypt with the KMS key Both statements in 4.6 are needed — ssm:GetParameters and kms:Decrypt. Also check the parameter path spelling exactly.
Task stops immediately, CannotPullContainerError No route to ECR Either the ECR interface endpoints are missing, or the private subnet's NAT route is broken. Both ecr.api and ecr.dkr are required, plus the S3 gateway endpoint for layers.
Redis connection hangs with no error redis:// where the cluster requires rediss:// Transit encryption is on; use two esses and include the auth token. Chapter 3.5.
Cognito login redirects to localhost:3000 The identity layer was never re-applied with the front-door URL Step 15 of the bootstrap. Re-apply 30-identity with front_door_url set.
Random 403s on form submissions after enabling the WAF AWSManagedRulesCommonRuleSet in block mode Put it back to count, read the sampled requests, add rule exclusions, then block. Chapter 6.2.
Server actions fail with an origin error CloudFront is not forwarding the Origin or Host header The origin request policy must be allViewerAndWhitelistCloudFront. Next enforces a same-origin check on server actions.
Terraform plan is full of (known after apply) nulls A remote state block missing workspace = terraform.workspace Chapter 3.8.
Prod resources appear with dev names, or the reverse Workspace and tfvars mismatch Add the workspace guard precondition from chapter 2.7.
Worker jobs run twice worker_desired_count > 1 Set it to 1. The sweeps are not concurrency-safe. Chapter 2.7.

8.7 — Decisions this guide could not make for you

Each of these needs the platform owner, not the person building infrastructure. Get answers before prod carries real data.

  1. Where does the jemba9.com zone live, and which unblock path? ALIAS record in another account, or re-delegate the registrar to a new zone in 824999955649. Chapter 6.5.
  2. Is us-west-2 right? This guide follows company.config.yaml. The Data Room handoff mentions us-east-2 and the stale workflows use us-east-1. Pick one deliberately and make the config the single source of truth.
  3. Lakebase or RDS? company.config.yaml says database: "lakebase-postgres" with RDS as the migration target. This guide provisions RDS because it is what the deployment plan and the migration runbook describe. If Lakebase stays, most of chapter 3 still applies — you skip the RDS resource and put the Lakebase connection strings into the same SSM parameters. Note that HANDOFF.md raises a real wrinkle: if Lakebase authenticates with Databricks OAuth tokens rather than a Postgres role, the pg pool needs a token-refresh wrapper.
  4. One investor org or one org per investor? HANDOFF.md §5.3. It changes how grants and expiries are issued, not infrastructure — but it determines what "tenant" means in the RLS policies you are relying on.
  5. Does the CRM stay in the Data Room? HANDOFF.md §5.4. Migrations 0003_crm.sql and 0004_crm_rls.sql already exist, so the default is yes.
  6. Who gets the budget alerts, and who approves prod deploys? Two named people. An unowned budget alarm and an unowned approval gate are both decorative.
  7. What is the recovery objective for prod? This guide sets 30-day backups with PITR. Whether that is right depends on an RPO nobody has written down, and the 730-day audit retention is a separate concern that backups do not satisfy on their own.

The one test that matters

Everything in these eight chapters exists to make this sentence true, from Applications/dataroom/docs/CHECKLIST.md:

Log in → open the app → perform a gated action → revoke the grant → the same action is denied on the next request.

If that works in an environment you built, the infrastructure is correct. If it does not, no amount of green health checks means anything.
