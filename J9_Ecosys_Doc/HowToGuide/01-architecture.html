1.1 — The building

The ecosystem's own metaphor, from Ecosystem/docs/architecture/j9-ecosystem-architecture.md, is a building. One front door where everyone signs in. A lobby that shows you which units you may enter. Units, which are the applications. And a key system that decides which doors open for whom.

The rule that follows from it, and the reason the infrastructure looks the way it does:

Authentication is decided in exactly one place (Cognito), authorization in exactly one place (the central authorization service), and apps own only their business logic.

So the OKR app has no login page. The Data Room has no user table. Both of them, on every protected read and every mutation, make a server-side call to the platform asking "may this identity do this thing?" and honour the answer. Which means the platform is not merely the first service you deploy — it is a hard runtime dependency of every other service in the building.

1.2 — The three deployables

The platform — Ecosystem/

Next.js 16 App Router, TypeScript strict, Prisma 6 against PostgreSQL 16, BullMQ on Redis 7, Tailwind 4. It serves the custom-branded login page, the portal launcher at /, the Admin app at /admin, the app registry, the audit viewer, the dashboards, and the two API surfaces every app depends on: GET /api/session and the can() decision endpoint. It also owns POST /api/events, which apps call to emit usage metrics.

It ships two processes from one image: npm start for the web app and npm run worker for the BullMQ worker. The worker runs the grant-expiry sweep (every 15 minutes per company.config.yaml), polls each registered app's /healthz, rolls up the event stream into daily summaries, and enforces the 730-day retention policy.

OKR — Applications/OKR/

Next.js 16 with basePath: "/okr", dev port 3001. Prisma 6 against its own PostgreSQL database using an okr schema. It declares 17 permissions and 6 metrics in okr.manifest.json, and it has its own Redis dependency for BullMQ — the nudge ladder, cycle gates, digests, and score sweeps described in CLAUDE.md.

Status in Applications/README.md: Migrating. The build is sequenced through numbered prompts under prompts/; treat the app as still in active construction and expect the schema to move. That is fine for infrastructure purposes — you are provisioning a database and a service, not freezing a schema.

Data Room — Applications/dataroom/

Next.js 16 with basePath: "/dataroom", dev port 8080. A React SPA mounted client-side, served by Next, calling same-origin BFF routes under app/api/*. It uses the raw pg driver rather than Prisma, and migrates with node scripts/db-migrate.mjs over plain SQL files in db/migrations/. It writes Excel exports with exceljs and sends mail through Resend.

Status: Migrating, not yet cut over. Per HANDOFF.md, the enforcement-point refactor is done — local auth stripped, can() delegation in place, RLS on every tenant table, events emitted, honest healthz — but Cognito provisioning, the real database swap, and the Supabase data copy are all still outstanding, and they need the platform owner, not you.

Two things about the Data Room that will bite you

Its package.json is still named vite_react_shadcn_ts and still carries vite, @vitejs/plugin-react-swc, and lovable-tagger as devDependencies. Harmless, but it means npm ci installs a build toolchain the app no longer uses.

Its two workflow files under .github/workflows/ deploy a static Vite bundle to a cloudcowboy-* S3 bucket in the wrong account, injecting Supabase environment variables that the app no longer reads. Delete both files before you connect this repo to Actions. If they run, they will fail loudly — but they will fail while assuming a role in someone else's account, which is worse than a plain failure.

1.4 — The six contracts that constrain your infrastructure

These are application-level rules, but each one forces an infrastructure decision. If you do not honour them, you will get a system that appears to work and is silently wrong.

1. Fail closed

From Applications/dataroom/CLAUDE.md: "Any non-allow — platform unreachable, timeout, malformed response — is DENIED. Never add a permissive fallback."

What this means for you: the app tasks must be able to reach the platform task with low latency and high reliability, or users see a functioning UI where every action is denied. Concretely: put the app-to-platform call on the internal ALB DNS name, not out through CloudFront and back; give the platform service at least two tasks in prod; set the ALB deregistration delay low enough that deploys do not strand in-flight can() calls; and alarm on platform 5xx separately from app 5xx, because a platform blip presents as a mass authorization failure rather than an outage.

2. Row-level security, keyed on a transaction-local setting

From Ecosystem/docs/architecture/rls.md. Every org-scoped table has RLS enabled and forced, with a policy comparing org_id to current_setting('app.current_org_id', true). When the setting is unset, current_setting returns NULL, org_id = NULL is never true, and the query matches no rows. Forgetting the context shows you nothing rather than everything.

What this means for you: the runtime database role must be neither a superuser nor the table owner, because superusers bypass RLS unconditionally. Each database therefore needs two roles — an owner that migrations run as, and a NOSUPERUSER NOBYPASSRLS role the application connects as. Two connection strings per database, two secrets, two different consumers.

3. Standard PostgreSQL only

NFR-3. No vendor extensions, no uuid-ossp, no pgcrypto — UUIDs are generated client-side by Prisma. The point is portability: moving between Lakebase, RDS, and Aurora is a connection-string change plus a data copy.

What this means for you: you can provision a plain aws_db_instance running postgres 16 with no custom parameter group beyond logging and TLS settings, and you must not introduce anything that would break the guarantee — no RDS Proxy-specific behaviour that the app depends on, no Aurora-only features, no rds.force_ssl off.

4. Path-based routing under one hostname

Each app sets basePath in next.config.ts, so every route, asset, and API endpoint already lives under its prefix. One cookie domain means one session across the whole building.

What this means for you: a single CloudFront distribution and a single ALB per environment, with path rules selecting the target group. It also means health checks must include the base path — a target group checking /healthz against the OKR service will get a 404 and mark every task unhealthy in a loop. The correct paths are /okr/healthz and /dataroom/healthz. This is the single most common way a first deployment of this system fails.

5. One secret per app: the app API key

J9_APP_API_KEY, a j9_... value issued on the app's detail page in Admin → Apps after its manifest is registered. Server-side only, never in the browser bundle.

What this means for you: a chicken-and-egg ordering problem. The app cannot authorize anything until it has a key; the key cannot be issued until the platform is running and an admin has registered the manifest. So the bootstrap order is: platform up → migrate and seed → register manifests → issue keys → write keys into SSM → deploy the app services. Chapter 8 sequences this.

6. Honest health endpoints

A /healthz returns 200 only when the app's database is actually reachable, and the platform's health worker treats a response slower than 2000 ms as degraded.

What this means for you: the ALB health check will legitimately fail when RDS is down, which is correct but means a database problem cascades into targets being deregistered. Set the health check thresholds generously — a 30-second interval with a threshold of 3 — so a brief database hiccup does not empty your target groups.

1.5 — Security posture you are inheriting

Ecosystem/docs/notes/security-baseline.md already sets the application-layer posture. Your job is not to re-decide it but to not undermine it:

Already handled in codeYour responsibility in AWS
Security headers including HSTS, set in next.config.ts Serve only over HTTPS so HSTS is honoured; redirect HTTP to HTTPS at CloudFront
Session cookies httpOnly, SameSite=Lax, Secure in production Do not terminate TLS anywhere that would make the app think it is on HTTP; forward the X-Forwarded-Proto header
Progressive lockout on login, 300 events/min/app ingest limit A WAF rate-based rule as the outer layer, tuned looser than the app's own limits
Append-only audit log and event stream, enforced by database triggers Backups and PITR long enough to satisfy the 730-day retention policy; never restore over a live audit table
Nothing secret in the repo; .env* and *.tfstate gitignored SSM SecureString and Secrets Manager, encrypted with a customer-managed KMS key; state bucket encrypted and versioned with public access blocked
Least-privilege database role per app Least-privilege task role per service — each service reads only its own SSM prefix
One open application-level item

The Content-Security-Policy still uses 'unsafe-inline' for scripts and styles, because the Next App Router injects an inline bootstrap. The baseline document tracks upgrading to a nonce plus 'strict-dynamic' before public launch, owned by the platform team. It is not an infrastructure task, but it is the thing to point at if someone asks whether the front door is launch-ready.

1.6 — What is genuinely not ready

Be honest with whoever asked you to do this. None of the following is your infrastructure work, and all of it sits between "dev environment green" and "customers using prod":

  1. No Dockerfiles exist. There is not a single Dockerfile in the repository. Chapter 5 gives you three. Two of them also need output: "standalone" added to next.config.ts — the platform deliberately keeps a full-dependency image, because its worker runs TypeScript source through tsx. Raise both as pull requests rather than applying them silently.
  2. Terraform covers only Cognito. Ecosystem/infra/terraform/ has one main.tf that provisions a user pool and a client, with a local state backend and a commented-out S3 backend stub. Everything else — network, data, secrets, compute, CDN, CI/CD — is described in docs/deployment/aws.md as modules to be written. This guide writes them.
  3. The Data Room cutover needs the platform owner. Five specific inputs are listed in HANDOFF.md §5: the app API key, the real database connection, whether investors get one shared org or one org each, whether the CRM stays in the app, and the investor invite list with expiries.
  4. DNS for jemba9.com is unresolved. The zone is not in the account you are building in. Chapter 6 covers both unblock paths. You do not need it to finish.
  5. The OKR app is mid-build. Provision for it, deploy it, but do not be surprised when its schema changes underneath you.
