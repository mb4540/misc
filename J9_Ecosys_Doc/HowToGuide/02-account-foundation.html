2.2 — Getting a shell that can do anything

You never create an IAM user and you never hold an access key. Configure an SSO profile once:

~/.aws/config

[sso-session onej9]
sso_start_url = https://onej9.awsapps.com/start
sso_region = us-west-2
sso_registration_scopes = sso:account:access

[profile j9]
sso_session = onej9
sso_account_id = 824999955649
sso_role_name = AdministratorAccess
region = us-west-2
output = json

# A narrower day-to-day profile once the foundation exists.
[profile j9-ro]
sso_session = onej9
sso_account_id = 824999955649
sso_role_name = ReadOnlyAccess
region = us-west-2
output = json
aws sso login --profile j9
aws sts get-caller-identity --profile j9
# Confirm the Account field reads 824999955649 before you run a single terraform apply.

export AWS_PROFILE=j9
export AWS_REGION=us-west-2
Set a shell guard

Because dev and prod share an account, a mistyped workspace is the realistic failure mode, not a mistyped account. Add this to your shell profile so your prompt always tells you which workspace is selected:

j9ws() { terraform workspace show 2>/dev/null; }
export PS1='[$(j9ws)] '$PS1

It looks trivial. It is the cheapest protection you will get against running a destroy against the wrong environment.

2.3 — Naming, so that nothing is ambiguous

Every resource in both environments carries the same prefix pattern. There are no unprefixed resources.

j9-<env>-<resource>            general form
j9-dev-vpc      j9-prod-vpc
j9-dev-alb      j9-prod-alb
j9-dev-pg       j9-prod-pg
j9-dev-redis    j9-prod-redis
j9-dev-users    j9-prod-users          (Cognito user pools)
j9-dev-cluster  j9-prod-cluster        (ECS)
j9-dev-platform j9-prod-platform       (ECS services; also -worker, -okr, -dataroom)

j9/<env>/<scope>/<name>        SSM parameter paths
j9/dev/platform/DATABASE_URL
j9/prod/okr/J9_APP_API_KEY

j9/<service>                   ECR repositories — NOT per environment
j9/platform  j9/okr  j9/dataroom

ECR repositories are deliberately shared between environments. That is what makes promotion honest: prod runs the exact image digest that passed in dev, not a rebuild of the same commit. See chapter 7.

Every resource also gets these tags, applied through the provider's default_tags so you cannot forget:

Project     = "jemba9-ecosystem"
Environment = "dev" | "prod"
ManagedBy   = "terraform"
Layer       = "network" | "data" | "identity" | "secrets" | "compute" | "frontdoor"

2.4 — How the two environments sit in one account

Two consequences worth internalising:

  • There is no network path between the environments. Separate VPCs, no peering, no transit gateway. A dev task cannot reach the prod database even if someone hands it the prod connection string, because the security group will not admit it and the subnet has no route.
  • IAM is the only shared blast radius. A policy that grants ssm:GetParameters on arn:aws:ssm:*:*:parameter/j9/* gives a dev task the prod secrets. Every IAM policy in this guide is scoped to /j9/${var.environment}/* for exactly that reason. Do not relax it.

2.5 — Guardrails, before anything expensive exists

Do these first. Each takes minutes and each has saved someone a bad month.

  1. Account-wide S3 public access block. One setting, no downside. 
    aws s3control put-public-access-block \
  --account-id 824999955649 \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
  2. EBS encryption by default and a default KMS key, in both regions you use. 
    aws ec2 enable-ebs-encryption-by-default --region us-west-2
aws ec2 enable-ebs-encryption-by-default --region us-east-1
  3. Budgets with alerts. Two budgets — one for the account, one filtered to Environment=dev — both alerting at 80% forecast and 100% actual. Terraform below.
  4. CloudTrail to a dedicated bucket, multi-region, log-file validation on. This is the only record of who changed what.
  5. GuardDuty enabled. Roughly the price of a coffee per month at this scale and it is the one security service that earns its keep with no configuration.
  6. Cost allocation tags activated for Environment and Layer, in Billing → Cost allocation tags. They take up to 24 hours to start populating, so switch them on today even though you will not need them for a fortnight.

2.6 — Terraform layout

The existing Ecosystem/infra/terraform/ holds one flat Cognito configuration. Restructure it into ordered layers, each with its own state, each reading the layer above through remote state outputs. This is more files than a single root module, and it buys you two things that matter: a terraform apply on the compute layer cannot possibly delete your database, and a plan takes seconds instead of minutes.

Ecosystem/infra/terraform/
├── 00-bootstrap/          state bucket, lock table, OIDC provider, budgets   [local state, run once]
├── 10-network/            VPC, subnets, NAT, security groups, endpoints
├── 20-data/               RDS, ElastiCache, S3 object bucket
├── 30-identity/           Cognito user pool + client   (move the existing main.tf here)
├── 40-secrets/            KMS key, SSM parameters, Secrets Manager
├── 50-compute/            ECR, ECS cluster, task defs, services, ALB
├── 60-frontdoor/          ACM (us-east-1), WAF, CloudFront, Route 53
└── shared/
    ├── backend.hcl        the S3 backend, passed with -backend-config
    ├── dev.tfvars
    └── prod.tfvars

The bootstrap layer

This one layer runs with local state, because it creates the bucket that all the other layers will store their state in. Once it has applied, you migrate its own state into the bucket it just made.

Ecosystem/infra/terraform/00-bootstrap/main.tf

# Bootstrap: the things every other layer depends on. Runs once, in us-west-2,
# against AWS account 824999955649. Local state initially, then migrated into
# the bucket this layer creates.

terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.60" }
  }
}

provider "aws" {
  region = "us-west-2"
  # Refuse to run against any other account. This single block is the reason a
  # stale credential cannot quietly build Jemba9 infrastructure somewhere else.
  allowed_account_ids = ["824999955649"]

  default_tags {
    tags = {
      Project   = "jemba9-ecosystem"
      ManagedBy = "terraform"
      Layer     = "bootstrap"
    }
  }
}

# ---------------------------------------------------------------- state backend
resource "aws_s3_bucket" "tf_state" {
  bucket = "j9-tf-state-824999955649"
}

resource "aws_s3_bucket_versioning" "tf_state" {
  bucket = aws_s3_bucket.tf_state.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "tf_state" {
  bucket = aws_s3_bucket.tf_state.id
  rule {
    apply_server_side_encryption_by_default { sse_algorithm = "AES256" }
  }
}

resource "aws_s3_bucket_public_access_block" "tf_state" {
  bucket                  = aws_s3_bucket.tf_state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

# Deny any non-TLS request to the state bucket.
resource "aws_s3_bucket_policy" "tf_state_tls_only" {
  bucket = aws_s3_bucket.tf_state.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "DenyInsecureTransport"
      Effect    = "Deny"
      Principal = "*"
      Action    = "s3:*"
      Resource = [
        aws_s3_bucket.tf_state.arn,
        "${aws_s3_bucket.tf_state.arn}/*",
      ]
      Condition = { Bool = { "aws:SecureTransport" = "false" } }
    }]
  })
}

resource "aws_dynamodb_table" "tf_locks" {
  name         = "j9-tf-locks"
  billing_mode = "PAY_PER_REQUEST"
  hash_key     = "LockID"
  attribute {
    name = "LockID"
    type = "S"
  }
  point_in_time_recovery { enabled = true }
}

# ------------------------------------------------------------- GitHub OIDC
# One provider for the whole account. The per-environment deploy roles that
# trust it live in 50-compute, where they can be scoped to real resource ARNs.
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  # GitHub rotates this; verify the current value before applying:
  #   https://docs.github.com/en/actions/deployment/security-hardening-your-deployments
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
}

# ------------------------------------------------------------------- budgets
resource "aws_budgets_budget" "account" {
  name         = "j9-account-monthly"
  budget_type  = "COST"
  limit_amount = "900"
  limit_unit   = "USD"
  time_unit    = "MONTHLY"

  notification {
    comparison_operator        = "GREATER_THAN"
    threshold                  = 80
    threshold_type             = "PERCENTAGE"
    notification_type          = "FORECASTED"
    subscriber_email_addresses = var.budget_alert_emails
  }

  notification {
    comparison_operator        = "GREATER_THAN"
    threshold                  = 100
    threshold_type             = "PERCENTAGE"
    notification_type          = "ACTUAL"
    subscriber_email_addresses = var.budget_alert_emails
  }
}

resource "aws_budgets_budget" "dev" {
  name         = "j9-dev-monthly"
  budget_type  = "COST"
  limit_amount = "250"
  limit_unit   = "USD"

  description = "Who hears about cost overruns."

Applying it, then moving its own state

cd Ecosystem/infra/terraform/00-bootstrap

terraform init
terraform plan  -var 'budget_alert_emails=["you@jemba9.com"]'
terraform apply -var 'budget_alert_emails=["you@jemba9.com"]'

# Now point this layer at the bucket it just created and move the state in.
cat >> main.tf <<'EOF'

terraform {
  backend "s3" {
    bucket         = "j9-tf-state-824999955649"
    key            = "bootstrap/terraform.tfstate"
    region         = "us-west-2"
    dynamodb_table = "j9-tf-locks"
    encrypt        = true
  }
}
EOF

terraform init -migrate-state    # answer yes
rm -f terraform.tfstate*         # the local copy is now redundant — and sensitive
Terraform 1.10 and newer

If your Terraform is 1.10+, you can replace dynamodb_table with use_lockfile = true and skip the DynamoDB table entirely — S3 now supports conditional writes for locking. The table is kept here because the repo's existing backend stub already names it and because it works on every version. Either is fine; do not use both.

2.7 — The shared backend and workspaces

Every layer from 10-network onwards uses the same backend file with a different key, and selects an environment through a workspace.

Ecosystem/infra/terraform/shared/backend.hcl

bucket         = "j9-tf-state-824999955649"
region         = "us-west-2"
dynamodb_table = "j9-tf-locks"
encrypt        = true

Ecosystem/infra/terraform/10-network/versions.tf (the same block in every layer)

terraform {
  required_version = ">= 1.6"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.60" }
  }
  backend "s3" {
    key = "network/terraform.tfstate"   # bucket/region/lock come from -backend-config
    # Workspaces keep dev and prod apart inside this key:
    #   env:/dev/network/terraform.tfstate
    #   env:/prod/network/terraform.tfstate
  }
}

provider "aws" {
  region              = var.region
  allowed_account_ids = ["824999955649"]

  default_tags {
    tags = {
      Project     = "jemba9-ecosystem"
      Environment = terraform.workspace
      ManagedBy   = "terraform"
      Layer       = "network"
    }
  }
}

locals {
  env    = terraform.workspace
  prefix = "j9-${terraform.workspace}"
  is_prod = terraform.workspace == "prod"
}

Because terraform.workspace drives the prefix, a resource cannot be created without an environment in its name. And because local.is_prod drives sizing, dev and prod differ by data, not by divergent code.

The working loop

cd Ecosystem/infra/terraform/10-network

terraform init -backend-config=../shared/backend.hcl

terraform workspace new dev          # first time
terraform workspace select dev

terraform plan  -var-file=../shared/dev.tfvars
terraform apply -var-file=../shared/dev.tfvars

# prod is the same commands with two words changed
terraform workspace select prod
terraform apply -var-file=../shared/prod.tfvars
The one mistake to avoid

terraform workspace select dev followed by -var-file=../shared/prod.tfvars will happily build prod-sized resources with dev names, or worse. Terraform will not stop you.

Guard it with a lifecycle precondition in every layer:

variable "environment" { type = string }

resource "null_resource" "workspace_guard" {
  lifecycle {
    precondition {
      condition     = var.environment == terraform.workspace
      error_message = "tfvars environment (${var.environment}) does not match workspace (${terraform.workspace})."
    }
  }
}

Set environment = "dev" in dev.tfvars and environment = "prod" in prod.tfvars. Now the mismatch fails at plan time instead of at 3am.

The two tfvars files

Ecosystem/infra/terraform/shared/dev.tfvars

environment = "dev"
region      = "us-west-2"

vpc_cidr            = "10.20.0.0/16"
single_nat_gateway  = true      # one NAT, ~$33/mo — dev does not need AZ-redundant egress

db_instance_class      = "db.t4g.micro"
db_allocated_storage   = 20
db_multi_az            = false
db_backup_retention    = 7
db_deletion_protection = false

redis_node_type        = "cache.t4g.micro"
redis_replicas         = 0

platform_desired_count = 1
okr_desired_count      = 1
dataroom_desired_count = 1
worker_desired_count   = 1
task_cpu               = 512
task_memory            = 1024

log_retention_days     = 14
enable_waf             = true
domain_name            = ""     # empty: serve on the CloudFront *.cloudfront.net hostname

Ecosystem/infra/terraform/shared/prod.tfvars

environment = "prod"
region      = "us-west-2"

vpc_cidr            = "10.30.0.0/16"
single_nat_gateway  = false     # one NAT per AZ — an AZ failure must not sever egress

db_instance_class      = "db.t4g.medium"
db_allocated_storage   = 100
db_multi_az            = true
db_backup_retention    = 30
db_deletion_protection = true

redis_node_type        = "cache.t4g.small"
redis_replicas         = 1      # automatic failover requires at least one replica

platform_desired_count = 2      # never one — fail-closed authz makes this the critical service
okr_desired_count      = 2
dataroom_desired_count = 2
worker_desired_count   = 1      # exactly one; the sweeps are not written to be run concurrently
task_cpu               = 1024
task_memory            = 2048

log_retention_days     = 365
enable_waf             = true
domain_name            = "jemba9.com"   # see chapter 6 before setting this
worker_desired_count is 1 on purpose

The worker runs the grant-expiry sweep, the health poll, the event rollup, and the retention prune. None of those are documented as safe to run concurrently, and the retention prune in particular temporarily disables a database trigger as the table owner. Two workers doing that at once is a genuinely bad time. Keep it at one, and accept the brief gap during a deploy — every job is a periodic sweep that will catch up on its next tick.

If you later want the worker to be highly available, the change belongs in the application (a Redis lock around each job), not in the task count.
