5.1 — Do this before you write a Dockerfile

The repository contains no Dockerfiles and none of the three Next configs sets an output mode. Two small code changes make containerisation straightforward. Raise them as pull requests in the app projects rather than editing quietly — they are build-behaviour changes and their owners should see them.

Change 1: standalone output for the two apps

Applications/OKR/next.config.ts — add one line

const nextConfig: NextConfig = {
  basePath: "/okr",
  output: "standalone",          // <-- add this
  reactStrictMode: true,
  serverExternalPackages: ["@prisma/client", ".prisma/client", "prisma"],
  turbopack: { root: import.meta.dirname },
  async headers() { /* unchanged */ },
};

Applications/dataroom/next.config.ts — add one line

const nextConfig: NextConfig = {
  basePath: BASE_PATH,
  output: "standalone",          // <-- add this
  reactStrictMode: true,
  env: { NEXT_PUBLIC_BASE_PATH: BASE_PATH },
};

output: "standalone" makes next build emit a self-contained .next/standalone directory with a server.js and only the node modules the server actually traced. The resulting image is roughly 200 MB instead of 1 GB, which matters on every deploy and every task start.

Change 2: the platform does not get standalone, and here is why

The worker is a tsx script, so the platform image keeps its dependencies

Ecosystem/package.json defines the worker as:

"worker": "NODE_OPTIONS=--conditions=react-server tsx src/worker/index.ts"

That runs TypeScript source directly, through tsx, which is a devDependency. A standalone build prunes both the source tree and every module the Next server did not trace — so the same image could serve the web app but not run the worker.

Rather than maintaining two platform images, build one image that keeps the full dependency tree and the source. It is larger (roughly 600 MB), and both npm start and npm run worker work from it unchanged. If the platform later adds a compiled worker entry point, switch it to standalone and the image drops to app size. Note it as a known cost, not a mystery.

HOSTNAME=0.0.0.0 is not optional

The Next standalone server reads HOSTNAME and defaults to localhost. Inside a Fargate task with awsvpc networking, a process bound to localhost is unreachable from the load balancer. The task will start, report healthy to Docker, log "ready in 400ms", and every ALB health check will time out.

It is set in all three Dockerfiles above. Do not remove it, and do not let a task definition override it.

5.3 — ECR

Three repositories, shared between environments. Image tags are the git SHA; promotion moves a digest.

Ecosystem/infra/terraform/50-compute/ecr.tf

# Repositories are NOT per environment — that is what makes dev-to-prod
# promotion a digest reference rather than a rebuild. Guard against the
# workspace loop creating them twice.
resource "aws_ecr_repository" "service" {
  for_each             = local.env == "prod" ? toset([]) : toset(["platform", "okr", "dataroom"])
  name                 = "j9/${each.key}"
  image_tag_mutability = "IMMUTABLE"

  image_scanning_configuration { scan_on_push = true }

  encryption_configuration {
    encryption_type = "KMS"
    kms_key         = data.terraform_remote_state.secrets.outputs.kms_key_arn
  }
}

resource "aws_ecr_lifecycle_policy" "service" {
  for_each   = aws_ecr_repository.service
  repository = each.value.name
  policy = jsonencode({
    rules = [
      {
        rulePriority = 1
        description  = "Keep the 30 most recent images"
        selection = {
          tagStatus   = "any"
          countType   = "imageCountMoreThan"
          countNumber = 30
        }
        action = { type = "expire" }
      },
    ]
  })
}
IMMUTABLE tags will catch a real mistake

With immutable tags, pushing a second image under the same tag fails. That is exactly what you want: it means a deployed SHA can never be quietly swapped for different bytes, and it means "prod is running abc1234" is a statement you can trust.

Because local.env == "prod" creates nothing, the repositories are created when you first apply the compute layer in the dev workspace, and the prod workspace looks them up with a data "aws_ecr_repository" instead. An alternative, arguably cleaner, is to move ECR into the 00-bootstrap layer, which has no workspaces at all.

5.5 — Task definitions

Written out for the platform, then for OKR. The worker reuses the platform definition with a command override; the Data Room is the OKR pattern with a different port, image, and secret set.

Ecosystem/infra/terraform/50-compute/task-platform.tf

locals {
  ssm = "arn:aws:ssm:${var.region}:824999955649:parameter/j9/${local.env}"

  # The internal URL app tasks use to reach the platform. Server-to-server —
  # never out through CloudFront and back, which would double latency and put a
  # WAF rate limit in front of your own authorization calls.
  platform_internal_url = "http://${aws_lb.internal.dns_name}"
}

resource "aws_ecs_task_definition" "platform" {
  family                   = "${local.prefix}-platform"
  requires_compatibilities = ["FARGATE"]
  network_mode             = "awsvpc"
  cpu                      = var.task_cpu
  memory                   = var.task_memory
  execution_role_arn       = aws_iam_role.exec["platform"].arn
  task_role_arn            = aws_iam_role.task["platform"].arn

  runtime_platform {
    operating_system_family = "LINUX"
    cpu_architecture        = "ARM64"      # Graviton: same price band, better price/performance
  }

  container_definitions = jsonencode([{
    name      = "platform"
    image     = "${data.aws_ecr_repository.platform.repository_url}:${var.platform_image_tag}"
    essential = true

    portMappings = [{ containerPort = 3000, protocol = "tcp" }]

    environment = [
      { name = "NODE_ENV",             value = "production" },
      { name = "PORT",                 value = "3000" },
      { name = "HOSTNAME",             value = "0.0.0.0" },
      { name = "AUTH_PROVIDER",        value = "cognito" },
      { name = "COGNITO_REGION",       value = var.region },
      { name = "SESSION_COOKIE_NAME",  value = "j9_session" },
      { name = "PLATFORM_SELF_URL",    value = var.front_door_url },
      { name = "J9_OBJECTS_BUCKET",    value = data.terraform_remote_state.data.outputs.objects_bucket },
    ]

    # Resolved by ECS at task start, using the execution role. The application
    # process never sees an SSM API call.
    secrets = [
      { name = "APP_DATABASE_URL",     valueFrom = "${local.ssm}/platform/APP_DATABASE_URL" },
      { name = "REDIS_URL",            valueFrom = "${local.ssm}/shared/REDIS_URL" },
      { name = "AUTH_CLIENT_ID",       valueFrom = "${local.ssm}/shared/COGNITO_CLIENT_ID" },
      { name = "COGNITO_USER_POOL_ID", valueFrom = "${local.ssm}/shared/COGNITO_USER_POOL_ID" },
      { name = "COGNITO_CLIENT_ID",    valueFrom = "${local.ssm}/shared/COGNITO_CLIENT_ID" },
    ]

    logConfiguration = {
      logDriver = "awslogs"
      options = {
        "awslogs-group"         = aws_cloudwatch_log_group.service["platform"].name
        "awslogs-region"        = var.region
        "awslogs-stream-prefix" = "platform"
      }
    }

    # A container-level check as well as the ALB check: this one catches a wedged
    # process before the load balancer does.
    healthCheck = {
      command     = ["CMD-SHELL", "wget -qO- http://127.0.0.1:3000/healthz || exit 1"]
      interval    = 30
      timeout     = 5
      retries     = 3
      startPeriod = 60
    }
  }])
}

5.7 — The load balancer

Two load balancers, and the second one is the part people forget.

  • j9-<env>-alb — internet-facing, in the public subnets, with its security group narrowed to the CloudFront origin-facing prefix list. This is what CloudFront talks to.
  • j9-<env>-alb-int — internal, in the private subnets. This is what the app tasks use to reach the platform for can() calls. Routing that traffic through the public ALB and CloudFront would work, and would be slower, more expensive, and subject to your own WAF rate limits.

Ecosystem/infra/terraform/50-compute/alb.tf

resource "aws_lb" "public" {
  name               = "${local.prefix}-alb"
  load_balancer_type = "application"
  internal           = false
  subnets            = data.terraform_remote_state.network.outputs.public_subnet_ids
  security_groups    = [data.terraform_remote_state.network.outputs.alb_sg_id]

  drop_invalid_header_fields = true
  enable_http2               = true
  idle_timeout               = 60

  access_logs {
    bucket  = aws_s3_bucket.alb_logs.id
    prefix  = "alb"
    enabled = true
  }

  enable_deletion_protection = local.is_prod
}

resource "aws_lb" "internal" {
  name               = "${local.prefix}-alb-int"
  load_balancer_type = "application"
  internal           = true
  subnets            = data.terraform_remote_state.network.outputs.private_subnet_ids
  security_groups    = [data.terraform_remote_state.network.outputs.task_sg_id]
  idle_timeout       = 30
}

# ---------------------------------------------------------------- target groups
resource "aws_lb_target_group" "service" {
  for_each = local.service_ports

  name        = "${local.prefix}-${each.key}-tg"
  port        = each.value
  protocol    = "HTTP"
  target_type = "ip"                # required for awsvpc / Fargate
  vpc_id      = data.terraform_remote_state.network.outputs.vpc_id

  # THE BASE PATH GOES IN THE HEALTH CHECK. This is the line that most often
  # gets copied wrong.
  health_check {
    enabled             = true
    path                = each.key == "platform" ? "/healthz" : "/${each.key}/healthz"
    matcher             = "200"
    interval            = 30
    timeout             = 5
    healthy_threshold   = 2
    unhealthy_threshold = 3
  }

  # Short, so a deploy does not strand in-flight can() calls; long enough that a
  # response in progress can finish.
  deregistration_delay = 20

  stickiness {
    enabled = false                 # sessions live in Redis, not in a task
    type    = "lb_cookie"
  }
}

# ------------------------------------------------------------------- listeners
resource "aws_lb_listener" "https" {
  load_balancer_arn = aws_lb.public.arn
  port              = 443
  protocol          = "HTTPS"
  ssl_policy        = "ELBSecurityPolicy-TLS13-1-2-2021-06"
  certificate_arn   = var.alb_certificate_arn      # regional cert, us-west-2

  # Default: reject anything that did not come through CloudFront.
  default_action {
    type = "fixed-response"
    fixed_response {
      content_type = "text/plain"
      message_body = "Direct access is not permitted."
      status_code  = "403"
    }
  }
}

# Rule 1 (priority 10): the shared secret proves the request came from our
# CloudFront distribution, not from someone who resolved the ALB hostname.
resource "aws_lb_listener_rule" "okr" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 10

  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.service["okr"].arn
  }

  condition {
    path_pattern { values = ["/okr", "/okr/*"] }
  }

  condition {
    http_header {
      http_header_name = "X-Origin-Verify"
      values           = [var.origin_verify_secret]
    }
  }
}

resource "aws_lb_listener_rule" "dataroom" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 20

  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.service["dataroom"].arn
  }

  condition {
    path_pattern { values = ["/dataroom", "/dataroom/*"] }
  }

  condition {
    http_header {
      http_header_name = "X-Origin-Verify"
      values           = [var.origin_verify_secret]
    }
  }
}

# Everything else that carries the secret goes to the platform.
resource "aws_lb_listener_rule" "platform" {
  listener_arn = aws_lb_listener.https.arn
  priority     = 100

  action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.service["platform"].arn
  }

  condition {
    http_header {
      http_header_name = "X-Origin-Verify"
      values           = [var.origin_verify_secret]
    }
  }
}

# The internal ALB carries only platform traffic and needs no verification —
# reaching it already requires being inside the VPC with the task security group.
resource "aws_lb_listener" "internal" {
  load_balancer_arn = aws_lb.internal.arn
  port              = 80
  protocol          = "HTTP"

  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.internal_platform.arn
  }
}

resource "aws_lb_target_group" "internal_platform" {
  name        = "${local.prefix}-plat-int-tg"
  port        = 3000
  protocol    = "HTTP"
  target_type = "ip"
  vpc_id      = data.terraform_remote_state.network.outputs.vpc_id

  health_check {
    path                = "/healthz"
    matcher             = "200"
    interval            = 15
    healthy_threshold   = 2
    unhealthy_threshold = 2
  }

  deregistration_delay = 10
}
The platform service registers with two target groups

An ECS service can have several load_balancer blocks. The platform needs both the public target group and the internal one, so its service definition gets two:

load_balancer {
  target_group_arn = aws_lb_target_group.service["platform"].arn
  container_name   = "platform"
  container_port   = 3000
}
load_balancer {
  target_group_arn = aws_lb_target_group.internal_platform.arn
  container_name   = "platform"
  container_port   = 3000
}

The for_each service resource above cannot express that cleanly. Split the platform out into its own aws_ecs_service resource with both blocks, and keep the for_each for okr and dataroom only. It is slightly more Terraform and much less surprising.

5.8 — Verifying compute before you put CloudFront in front of it

Do not add the CDN until the ALB works. Debugging through a cache is miserable.

# 1. Are the tasks running?
aws ecs describe-services --cluster j9-dev-cluster \
  --services j9-dev-platform j9-dev-okr j9-dev-dataroom j9-dev-worker \
  --query 'services[].{name:serviceName,running:runningCount,desired:desiredCount}'

# 2. Are the targets healthy? This is where the base-path mistake shows up.
for tg in platform okr dataroom; do
  echo "== $tg"
  aws elbv2 describe-target-health \
    --target-group-arn "$(aws elbv2 describe-target-groups \
        --names "j9-dev-$tg-tg" --query 'TargetGroups[0].TargetGroupArn' --output text)" \
    --query 'TargetHealthDescriptions[].TargetHealth.{state:State,reason:Reason,desc:Description}'
done

# 3. Talk to the ALB directly, supplying the header CloudFront would add.
#    Temporarily widen the ALB security group to your own IP to do this.
ALB=$(aws elbv2 describe-load-balancers --names j9-dev-alb \
      --query 'LoadBalancers[0].DNSName' --output text)

curl -sk -H "X-Origin-Verify: $SECRET" "https://$ALB/healthz"           | head
curl -sk -H "X-Origin-Verify: $SECRET" "https://$ALB/okr/healthz"       | head
curl -sk -H "X-Origin-Verify: $SECRET" "https://$ALB/dataroom/healthz"  | head

# 4. Without the header: expect 403.
curl -sk -o /dev/null -w '%{http_code}\n' "https://$ALB/healthz"

# 5. Get a shell in a task if something is wrong.
aws ecs execute-command --cluster j9-dev-cluster \
  --task "$(aws ecs list-tasks --cluster j9-dev-cluster --service-name j9-dev-okr \
            --query 'taskArns[0]' --output text)" \
  --container okr --interactive --command "/bin/sh"
What good looks like

All four services at running == desired. All three target groups reporting healthy. The three /healthz curls returning 200 with a JSON body. The unheadered curl returning 403. A worker log stream showing the grant-expiry sweep firing on its 15-minute cadence.

If the OKR or Data Room healthz returns 200 but a real page denies everything, that is the task-to-task security group rule — chapter 3.2.
