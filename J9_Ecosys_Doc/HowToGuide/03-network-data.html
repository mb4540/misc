3.1 — The network

Three tiers, two AZs, six subnets. The reasoning:

  • Public holds the ALB nodes and the NAT gateways. Nothing else. No EC2, no tasks.
  • Private holds the Fargate tasks. They reach the internet through NAT and reach AWS APIs through VPC endpoints, which is both cheaper and faster than routing ECR pulls through NAT.
  • Isolated holds RDS and ElastiCache and has no route table entry pointing anywhere outside the VPC. Not to a NAT gateway, not to an internet gateway. If a task is compromised, the database is still only reachable on the paths the security groups allow.
The NAT gateway is your biggest fixed cost

A NAT gateway is roughly 32–35 USD per month before data processing, per AZ. In dev, single_nat_gateway = true gives you one. In prod you want one per AZ so that losing an AZ does not sever egress for the surviving tasks.

You can go further: only the Data Room genuinely needs internet egress (the Resend mail API), and the platform needs Cognito and SES. If you add VPC endpoints for everything else and are willing to give the Data Room task its own narrower path, you could drop NAT entirely in dev. That is an optimisation for month two, not week one — the debugging cost of a missing endpoint exceeds 33 dollars.

3.2 — Security groups as a chain, not a list of CIDRs

Every rule below references another security group rather than an address range. That means you can resize subnets, add AZs, or move a service and none of the rules need editing. It also means a reader can see the intended data flow by reading the group names.

Ecosystem/infra/terraform/10-network/security-groups.tf

# ALB — the only thing with an ingress rule from outside the VPC, and even that is
# narrowed to CloudFront's own address ranges via a managed prefix list.
data "aws_ec2_managed_prefix_list" "cloudfront" {
  name = "com.amazonaws.global.cloudfront.origin-facing"
}

resource "aws_security_group" "alb" {
  name        = "${local.prefix}-alb-sg"
  description = "Public entry point. CloudFront only."
  vpc_id      = aws_vpc.main.id

  ingress {
    description     = "HTTPS from CloudFront edge locations only"
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    prefix_list_ids = [data.aws_ec2_managed_prefix_list.cloudfront.id]
  }

  egress {
    description = "To the task security group"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = [var.vpc_cidr]
  }

  tags = { Name = "${local.prefix}-alb-sg" }
}

# All four Fargate services share one security group. They are peers: the OKR task
# calling the platform task is the same trust relationship as the reverse.
resource "aws_security_group" "task" {
  name        = "${local.prefix}-task-sg"
  description = "Fargate tasks."
  vpc_id      = aws_vpc.main.id

  ingress {
    description     = "From the ALB"
    from_port       = 3000
    to_port         = 8080
    protocol        = "tcp"
    security_groups = [aws_security_group.alb.id]
  }

  ingress {
    description = "Task to task — this is what makes fail-closed authz work"
    from_port   = 3000
    to_port     = 8080
    protocol    = "tcp"
    self        = true
  }

  egress {
    description = "Anywhere: AWS APIs via endpoints, Resend and Cognito via NAT"
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }

  tags = { Name = "${local.prefix}-task-sg" }
}

resource "aws_security_group" "database" {
  name        = "${local.prefix}-db-sg"
  description = "RDS. Reachable only from tasks."
  vpc_id      = aws_vpc.main.id

  ingress {
    description     = "PostgreSQL from tasks"
    from_port       = 5432
    to_port         = 5432
    protocol        = "tcp"
    security_groups = [aws_security_group.task.id]
  }

  # No egress rule at all. RDS does not initiate connections.
  tags = { Name = "${local.prefix}-db-sg" }
}

resource "aws_security_group" "cache" {
  name        = "${local.prefix}-cache-sg"
  description = "ElastiCache. Reachable only from tasks."
  vpc_id      = aws_vpc.main.id

  ingress {
    description     = "Redis from tasks"
    from_port       = 6379
    to_port         = 6379
    protocol        = "tcp"
    security_groups = [aws_security_group.task.id]
  }

  tags = { Name = "${local.prefix}-cache-sg" }
}

resource "aws_security_group" "vpce" {
  name        = "${local.prefix}-vpce-sg"
  description = "Interface VPC endpoints."
  vpc_id      = aws_vpc.main.id

  ingress {
    description     = "HTTPS from tasks"
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.task.id]
  }

  tags = { Name = "${local.prefix}-vpce-sg" }

The task-to-task rule is not optional

Delete the self = true ingress rule and the system will come up, serve the login page, show the portal, and then deny every single action in both apps — because the OKR and Data Room tasks will time out calling the platform's can() endpoint, and a timeout is a DENY by design.

The symptom is maddening: healthy targets, 200 responses, no errors in the app logs, and users who cannot do anything. If you ever see that pattern, check this rule first.

3.3 — VPC endpoints

Five interface endpoints and one gateway endpoint. The interface endpoints cost about 7–8 USD each per month per AZ, so in dev this is a real line item — but ECR pulls through NAT cost data-processing charges on every deploy, and the S3 gateway endpoint is free and eliminates the largest share of that traffic.

Ecosystem/infra/terraform/10-network/endpoints.tf

# Free. Do this one even if you skip the others.
resource "aws_vpc_endpoint" "s3" {
  vpc_id            = aws_vpc.main.id
  service_name      = "com.amazonaws.${var.region}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = concat(aws_route_table.private[*].id, [aws_route_table.isolated.id])
  tags              = { Name = "${local.prefix}-vpce-s3" }
}

locals {
  interface_endpoints = {
    ecr_api = "ecr.api"          # authenticating to ECR
    ecr_dkr = "ecr.dkr"          # pulling image layers
    logs    = "logs"             # CloudWatch Logs from the awslogs driver
    ssm     = "ssm"              # reading SSM parameters at task boot
    secrets = "secretsmanager"   # reading the RDS master secret
  }
}

resource "aws_vpc_endpoint" "interface" {
  for_each            = local.interface_endpoints
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${var.region}.${each.value}"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.vpce.id]
  private_dns_enabled = true
  tags                = { Name = "${local.prefix}-vpce-${each.key}" }
}

One instance per environment, holding three databases. Not three instances — the databases are logically isolated by ownership and role grants, which is exactly what the architecture document describes ("each future app gets its own schema (or database) with credentials scoped to it"), and it keeps the bill sane.

  maintenance_window      = "Sun:10:30-Sun:11:30"

  # Audit retention is 730 days (company.config.yaml). PITR covers operational

Why manage_master_user_password

It puts the master credential in Secrets Manager with AWS-managed rotation, so no password is ever in your Terraform state, your tfvars, or your terminal history. The tradeoff is that you cannot read the password in a terraform output — which is the point. Chapter 3.6 shows how to run the bootstrap SQL without ever seeing it.

Transit encryption changes the connection URL

With transit_encryption_enabled = true and an auth token, the connection string is rediss:// — two esses — with the token as the password:

rediss://:TOKEN@j9-dev-redis.xxxxx.ng.0001.usw2.cache.amazonaws.com:6379

The repo's .env.example uses redis://localhost:6380 with no auth. ioredis handles rediss:// natively, so no code change is needed — but if you write redis:// into the SSM parameter, the connection will hang rather than fail cleanly, and you will spend an afternoon on it.

3.6 — Three databases, six roles

Terraform creates the instance. SQL creates the databases and roles. Run it once per environment, immediately after the instance is available, before any migration.

Ecosystem/infra/terraform/20-data/bootstrap.sql

-- Run as the RDS master user, once per environment, before any migration.
-- Creates three databases, each with an owner role (migrations) and a
-- least-privilege runtime role (RLS-enforced). Mirrors, in a managed
-- environment, what docker/postgres-init/01-init-roles-and-shadow.sql and
-- Applications/dataroom/db/init/01-roles-and-schema.sql do locally.
--
-- Passwords are placeholders: substitute the generated values, and put those
-- same values into SSM (chapter 4). Never commit real ones.

-- ============================================================ platform
CREATE ROLE j9      WITH LOGIN PASSWORD :'j9_pw'      NOSUPERUSER CREATEDB NOCREATEROLE;
CREATE ROLE j9_app  WITH LOGIN PASSWORD :'j9_app_pw'  NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;

-- j9_platform already exists (db_name on the instance). Hand it to the owner.
ALTER DATABASE j9_platform OWNER TO j9;
GRANT CONNECT ON DATABASE j9_platform TO j9_app;

-- ================================================================= okr
CREATE ROLE okr     WITH LOGIN PASSWORD :'okr_pw'     NOSUPERUSER CREATEDB NOCREATEROLE;
CREATE ROLE okr_app WITH LOGIN PASSWORD :'okr_app_pw' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
CREATE DATABASE okr OWNER okr;
GRANT CONNECT ON DATABASE okr TO okr_app;

-- ============================================================ dataroom
CREATE ROLE dataroom     WITH LOGIN PASSWORD :'dr_pw'     NOSUPERUSER CREATEDB NOCREATEROLE;
CREATE ROLE dataroom_app WITH LOGIN PASSWORD :'dr_app_pw' NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;
CREATE DATABASE dataroom OWNER dataroom;
GRANT CONNECT ON DATABASE dataroom TO dataroom_app;

Ecosystem/infra/terraform/20-data/bootstrap-dataroom.sql

-- Connect to the `dataroom` database AS the `dataroom` owner and run this.
-- Identical in intent to db/init/01-roles-and-schema.sql, which only runs on a
-- fresh Docker container and therefore never runs against RDS.

CREATE SCHEMA IF NOT EXISTS dataroom AUTHORIZATION dataroom;

GRANT USAGE ON SCHEMA dataroom TO dataroom_app;

ALTER DEFAULT PRIVILEGES FOR ROLE dataroom IN SCHEMA dataroom
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO dataroom_app;
ALTER DEFAULT PRIVILEGES FOR ROLE dataroom IN SCHEMA dataroom
  GRANT USAGE, SELECT ON SEQUENCES TO dataroom_app;

-- Keep the runtime role out of public entirely.
REVOKE ALL ON SCHEMA public FROM dataroom_app;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
The platform migration also grants and enables RLS

For j9_platform, the table grants to j9_app and the RLS policies are inside the Prisma migration 20260714173418_constraints_rls, so they travel with prisma migrate deploy and you do not repeat them here. The same is true of the Data Room's db/migrations/0002_rls.sql and 0004_crm_rls.sql.

What does not travel is the role creation and the schema authorization above — those only exist in Docker init scripts, which never run on RDS. Missing them is the second most common first-deploy failure after the health-check path.

Running the bootstrap SQL without a bastion host

The database is in an isolated subnet with no inbound path from the internet, which is correct and means you cannot simply psql at it. Two ways in, neither requiring a bastion EC2 instance:

Option A — a one-off ECS task (preferred)

# Build a tiny image once: postgres client + the two SQL files.
cat > infra/dbadmin/Dockerfile <<'EOF'
FROM postgres:16-alpine
COPY *.sql /sql/
ENTRYPOINT ["/bin/sh","-c"]
EOF

# Push it to ECR as j9/dbadmin, then run it inside the VPC with the task SG,
# passing the master secret in as an environment secret. It has network reach
# to RDS because it is in the private subnets with the task security group.
aws ecs run-task \
  --cluster j9-dev-cluster \
  --task-definition j9-dev-dbadmin \
  --launch-type FARGATE \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-aaa,subnet-bbb],securityGroups=[sg-task],assignPublicIp=DISABLED}' \
  --overrides '{"containerOverrides":[{"name":"dbadmin","command":["psql \"$MASTER_URL\" -v j9_pw=... -f /sql/bootstrap.sql"]}]}'

Option B — SSM port forwarding through a throwaway instance

If you would rather work interactively while developing, start a t4g.nano in a private subnet with the SSM agent and the task security group, then forward a local port. No SSH key, no inbound rule, and you delete it afterwards.

aws ssm start-session \
  --target i-0123456789abcdef0 \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["j9-dev-pg.xxxxx.us-west-2.rds.amazonaws.com"],"portNumber":["5432"],"localPortNumber":["5433"]}'

# Now, in another shell — note it lands on 5433, the same port the repo's local
# docker-compose uses, so every documented psql command works unchanged.
psql "postgresql://j9_master:...@localhost:5433/j9_platform?sslmode=require"
Verify before you move on 
-- As each app role, confirm it cannot bypass RLS:
SELECT rolname, rolsuper, rolbypassrls FROM pg_roles
WHERE rolname IN ('j9','j9_app','okr','okr_app','dataroom','dataroom_app');
-- Every *_app row must read: rolsuper=f, rolbypassrls=f

If rolbypassrls is true for any _app role, row-level security is silently doing nothing and every org can read every other org's data. Fix it before you load any real data.

3.7 — S3

One object bucket per environment, with a prefix per app, matching the architecture's "S3 with per-app prefixes, signed URLs only". Plus two log buckets.

Ecosystem/infra/terraform/20-data/s3.tf

resource "aws_s3_bucket" "objects" {
  bucket = "${local.prefix}-objects-824999955649"
}

resource "aws_s3_bucket_public_access_block" "objects" {
  bucket                  = aws_s3_bucket.objects.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

resource "aws_s3_bucket_server_side_encryption_configuration" "objects" {
  bucket = aws_s3_bucket.objects.id
  rule {
    apply_server_side_encryption_by_default {
      sse_algorithm     = "aws:kms"
      kms_master_key_id = data.terraform_remote_state.secrets.outputs.kms_key_arn
    }
    bucket_key_enabled = true      # cuts KMS request cost substantially
  }
}

resource "aws_s3_bucket_versioning" "objects" {
  bucket = aws_s3_bucket.objects.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_lifecycle_configuration" "objects" {
  bucket = aws_s3_bucket.objects.id

  rule {
    id     = "expire-old-versions"
    status = "Enabled"
    noncurrent_version_expiration { noncurrent_days = 90 }
    abort_incomplete_multipart_upload { days_after_initiation = 7 }
  }

  # Exports are regenerable; do not pay to keep them forever.
  rule {
    id     = "expire-dataroom-exports"
    status = "Enabled"
    filter { prefix = "dataroom/exports/" }
    expiration { days = 180 }
  }
}

resource "aws_s3_bucket_policy" "objects_tls_only" {
  bucket = aws_s3_bucket.objects.id
  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Sid       = "DenyInsecureTransport"
      Effect    = "Deny"
      Principal = "*"
      Action    = "s3:*"
      Resource  = [aws_s3_bucket.objects.arn, "${aws_s3_bucket.objects.arn}/*"]
      Condition = { Bool = { "aws:SecureTransport" = "false" } }
    }]
  })
}

s3://j9-<env>-objects-824999955649/
├── platform/          branding overrides, admin exports
├── okr/               attachments on objectives and check-ins
└── dataroom/

Ecosystem/infra/terraform/50-compute/remote-state.tf (pattern)

data "terraform_remote_state" "network" {
  backend   = "s3"
  workspace = terraform.workspace       # this is what keeps dev reading dev
  config = {
    bucket = "j9-tf-state-824999955649"
    key    = "network/terraform.tfstate"
    region = "us-west-2"
  }
}
workspace = terraform.workspace matters

Omit that line and every layer reads the default workspace's state, which is empty. You will get a plan full of (known after apply) nulls and errors about empty lists. It is a one-line mistake with a very confusing signature.
