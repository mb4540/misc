4.1 — One customer-managed KMS key per environment

Everything encrypted in an environment uses the same key: RDS storage, the RDS master secret, Redis at rest, S3 objects, SSM SecureStrings, and CloudWatch log groups. One key per environment means a single place to audit grants, and it means a dev key cannot decrypt prod data.

Ecosystem/infra/terraform/40-secrets/kms.tf

resource "aws_kms_key" "main" {
  description             = "Jemba9 ${local.env} — application data and secrets."
  enable_key_rotation     = true
  deletion_window_in_days = local.is_prod ? 30 : 7
  tags                    = { Name = "${local.prefix}-key" }
}

resource "aws_kms_alias" "main" {
  name          = "alias/${local.prefix}"
  target_key_id = aws_kms_key.main.key_id
}

# CloudWatch Logs needs an explicit grant in the key policy to encrypt log groups.
data "aws_iam_policy_document" "kms" {
  statement {
    sid       = "AccountRoot"
    effect    = "Allow"
    actions   = ["kms:*"]
    resources = ["*"]
    principals {
      type        = "AWS"
      identifiers = ["arn:aws:iam::824999955649:root"]
    }
  }

  statement {
    sid    = "CloudWatchLogs"
    effect = "Allow"
    actions = [
      "kms:Encrypt", "kms:Decrypt", "kms:ReEncrypt*",
      "kms:GenerateDataKey*", "kms:Describe*",
    ]
    resources = ["*"]
    principals {
      type        = "Service"
      identifiers = ["logs.${var.region}.amazonaws.com"]
    }
    condition {
      test     = "ArnLike"
      variable = "kms:EncryptionContext:aws:logs:arn"
      values   = ["arn:aws:logs:${var.region}:824999955649:log-group:/j9/${local.env}/*"]
    }
  }
}

resource "aws_kms_key_policy" "main" {
  key_id = aws_kms_key.main.id
  policy = data.aws_iam_policy_document.kms.json
}

4.2 — The SSM parameter tree

Every runtime value the containers read lives at /j9/<env>/<scope>/<NAME>. The scope is either a service name or shared. This layout is not cosmetic — the task role IAM policies are written against these paths, so the shape of the tree is the access-control model.

/j9/dev/shared/
    REDIS_URL                     rediss://:TOKEN@host:6379
    COGNITO_REGION                us-west-2
    COGNITO_USER_POOL_ID          us-west-2_xxxxxxxxx
    COGNITO_CLIENT_ID             xxxxxxxxxxxxxxxxxxxxxxxxxx
    PLATFORM_SELF_URL             https://dxxxxxxxxxxxxx.cloudfront.net
    J9_PLATFORM_INTERNAL_URL      http://j9-dev-alb-internal-...:80

/j9/dev/platform/
    DATABASE_URL                  owner   — used ONLY by the migration task
    APP_DATABASE_URL              runtime — j9_app, RLS enforced
    SESSION_COOKIE_NAME           j9_session
    AUTH_PROVIDER                 cognito
    AUTH_CLIENT_ID                (mirrors COGNITO_CLIENT_ID)

/j9/dev/okr/
    DATABASE_URL                  owner   — migration task only
    APP_DATABASE_URL              runtime — okr_app
    J9_APP_API_KEY                j9_... issued in Admin -> Apps

/j9/dev/dataroom/
    DATABASE_URL                  owner   — migration task only
    APP_DATABASE_URL              runtime — dataroom_app
    J9_APP_API_KEY                j9_...
    RESEND_API_KEY                re_...
    NEXT_PUBLIC_PLATFORM_PORTAL_URL   the front-door URL for the signed-out redirect

/j9/dev/frontdoor/
    ORIGIN_VERIFY_SECRET          shared between CloudFront and the ALB listener rule
Two connection strings per database, and only one goes to the app

DATABASE_URL is the owner credential. It exists so migrations can run. It must be readable by the migration task role and by nothing else — not by the platform service, not by the app services. If a running application connects as the owner, it bypasses row-level security and every tenant can read every other tenant's rows. The application reads APP_DATABASE_URL only.

This is the single most consequential configuration decision in the whole build. The repo's .env.example files already make the distinction; do not collapse it in AWS because it is inconvenient.

Creating the parameters

Values that Terraform can derive, it should. Values a human must paste — the app API keys, the Resend key — get an ignore_changes lifecycle so Terraform creates the parameter once with a placeholder and then never fights whoever filled it in.

Ecosystem/infra/terraform/40-secrets/parameters.tf

locals {
  db_host = data.terraform_remote_state.data.outputs.db_address
  db_port = data.terraform_remote_state.data.outputs.db_port

  # sslmode=require is mandatory: rds.force_ssl=1 is set in the parameter group.
  conn = {
    platform_owner = "postgresql://j9:${var.pw_j9}@${local.db_host}:${local.db_port}/j9_platform?sslmode=require"
    platform_app   = "postgresql://j9_app:${var.pw_j9_app}@${local.db_host}:${local.db_port}/j9_platform?sslmode=require"
    okr_owner      = "postgresql://okr:${var.pw_okr}@${local.db_host}:${local.db_port}/okr?sslmode=require"
    okr_app        = "postgresql://okr_app:${var.pw_okr_app}@${local.db_host}:${local.db_port}/okr?sslmode=require"
    dr_owner       = "postgresql://dataroom:${var.pw_dr}@${local.db_host}:${local.db_port}/dataroom?sslmode=require&schema=dataroom"
    dr_app         = "postgresql://dataroom_app:${var.pw_dr_app}@${local.db_host}:${local.db_port}/dataroom?sslmode=require&schema=dataroom"
  }

  derived = {
    "shared/REDIS_URL"            = "rediss://:${data.terraform_remote_state.data.outputs.redis_auth_token}@${data.terraform_remote_state.data.outputs.redis_primary_endpoint}:6379"
    "shared/COGNITO_REGION"       = var.region
    "shared/COGNITO_USER_POOL_ID" = data.terraform_remote_state.identity.outputs.user_pool_id
    "shared/COGNITO_CLIENT_ID"    = data.terraform_remote_state.identity.outputs.user_pool_client_id
    "platform/DATABASE_URL"       = local.conn.platform_owner
    "platform/APP_DATABASE_URL"   = local.conn.platform_app
    "platform/AUTH_PROVIDER"      = "cognito"
    "platform/SESSION_COOKIE_NAME" = "j9_session"
    "okr/DATABASE_URL"            = local.conn.okr_owner
    "okr/APP_DATABASE_URL"        = local.conn.okr_app
    "dataroom/DATABASE_URL"       = local.conn.dr_owner
    "dataroom/APP_DATABASE_URL"   = local.conn.dr_app
  }

  # Filled in by a human, after the platform is running.
  placeholders = [
    "okr/J9_APP_API_KEY",
    "dataroom/J9_APP_API_KEY",
    "dataroom/RESEND_API_KEY",
  ]
}

resource "aws_ssm_parameter" "derived" {
  for_each = local.derived
  name     = "/j9/${local.env}/${each.key}"
  type     = "SecureString"
  key_id   = aws_kms_key.main.arn
  value    = each.value
  tier     = "Standard"
  tags     = { Scope = split("/", each.key)[0] }
}

resource "aws_ssm_parameter" "placeholder" {
  for_each = toset(local.placeholders)
  name     = "/j9/${local.env}/${each.value}"
  type     = "SecureString"
  key_id   = aws_kms_key.main.arn
  value    = "PLACEHOLDER-REPLACE-ME"

  lifecycle {
    ignore_changes = [value]   # a human owns this value from now on
  }
}

The role passwords themselves are generated once, outside Terraform, and passed in as sensitive variables so they never appear in a repository. Generate and store them in one step:

# Generate six passwords and write them straight into a gitignored tfvars file.
gen() { openssl rand -base64 32 | tr -d '/+=' | cut -c1-28; }

cat > shared/dev.secret.tfvars <<EOF
pw_j9        = "$(gen)"
pw_j9_app    = "$(gen)"
pw_okr       = "$(gen)"
pw_okr_app   = "$(gen)"
pw_dr        = "$(gen)"
pw_dr_app    = "$(gen)"
EOF

chmod 600 shared/dev.secret.tfvars
echo '*.secret.tfvars' >> ../../.gitignore     # the repo already ignores *.tfvars, but be explicit

# These are the same values you substitute into bootstrap.sql in chapter 3.
terraform apply -var-file=../shared/dev.tfvars -var-file=../shared/dev.secret.tfvars
These passwords land in Terraform state

They do, and that is why the state bucket is encrypted, versioned, TLS-only, and public-access-blocked. If that is not acceptable to whoever owns security here, the alternative is to create each role's credential directly in Secrets Manager with a rotation Lambda and have the parameters reference the secret rather than hold the value. That is more machinery for a marginal gain at this scale; raise it as a decision rather than deciding it silently.

4.3 — Cognito, one pool per environment

The repo already has a working Cognito configuration at Ecosystem/infra/terraform/main.tf: a user pool with email as username, a NIST-leaning password policy, optional TOTP MFA, admin-create-only invites, verified-email recovery, and a public PKCE client with no secret and short-lived tokens. Move that file to 30-identity/ essentially unchanged. Three things need to change.

Ecosystem/infra/terraform/30-identity/main.tf (the changed parts only)

# 1. Name it per workspace, so dev and prod get separate pools.
resource "aws_cognito_user_pool" "platform" {
  name = "${local.prefix}-users"        # was: "${var.company_slug}-${var.environment}-users"
  # ... everything else from the existing main.tf is correct as written ...
}

# 2. Callback URLs come from the front door, which does not exist yet on the
#    first pass. Apply this layer twice: once with the localhost values, then
#    again after 60-frontdoor with the real hostname.
resource "aws_cognito_user_pool_client" "web" {
  name         = "${local.prefix}-web"
  user_pool_id = aws_cognito_user_pool.platform.id

  generate_secret = false
  explicit_auth_flows = [
    "ALLOW_USER_PASSWORD_AUTH",
    "ALLOW_USER_SRP_AUTH",
    "ALLOW_REFRESH_TOKEN_AUTH",
  ]
  allowed_oauth_flows_user_pool_client = true
  allowed_oauth_flows                  = ["code"]
  allowed_oauth_scopes                 = ["openid", "email", "profile"]
  supported_identity_providers         = ["COGNITO"]

  callback_urls = var.front_door_url == "" ? ["http://localhost:3000/api/auth/callback"] : [

  id_token_validity      = 1
  access_token_validity  = 1
  refresh_token_validity = 8

    id_token      = "hours"
    access_token  = "hours"
    refresh_token = "hours"

# 3. Production sends its own mail. Cognito's default sender is rate-limited to
#    about 50 messages a day and cannot use your domain — fine for dev, not for
#    inviting investors.
resource "aws_ses_domain_identity" "main" {

  domain = var.domain_name

resource "aws_ses_domain_dkim" "main" {
  count  = local.is_prod ? 1 : 0
  domain = aws_ses_domain_identity.main[0].domain

SES starts in the sandbox

A new SES identity can only send to verified addresses until you request production access, which is a support ticket that takes a day or two. Do it early — it is on nobody's critical path until suddenly it is the thing blocking the first real investor invite.

Until then, dev runs on email_sending_account = "COGNITO_DEFAULT", exactly as the existing Terraform already handles through the ses_source_arn == "" conditional.

The MFA nuance you should not "fix"

mfa_configuration is OPTIONAL at the pool level, and an admin_roles Cognito group exists. That combination looks like a mistake and is not: per company.config.yaml, identity.mfa_required lists internal_orgs and admin_roles, and the application enforces MFA for those groups. Setting the pool to ON would force MFA on invited external investors too, which is deliberately not the policy. Leave it alone.

4.4 — The app API keys, and the ordering problem

Each app needs a J9_APP_API_KEY to call the platform. The key is issued in the Admin app, which runs on the platform, which must therefore be deployed and seeded first. The sequence:

  1. Deploy the platform service and the worker. They need no app keys.
  2. Run prisma migrate deploy then npm run seed against j9_platform. The seed creates the internal org, the reserved platform app, and the Admin app with its permissions and system roles, all from company.config.yaml.
  3. Bootstrap the first Org Admin and sign in through the front door.
  4. In Admin → Apps, import Applications/OKR/okr.manifest.json and Applications/dataroom/manifest.json (Preview, then Apply).
  5. On each app's detail page, issue an API key. Copy it immediately — you will not be shown it again.
  6. Write each key into SSM: 
    aws ssm put-parameter --overwrite \
  --name /j9/dev/okr/J9_APP_API_KEY \
  --type SecureString --key-id alias/j9-dev \
  --value 'j9_...'

aws ssm put-parameter --overwrite \
  --name /j9/dev/dataroom/J9_APP_API_KEY \
  --type SecureString --key-id alias/j9-dev \
  --value 'j9_...'
  7. Force a new deployment of the two app services so their tasks pick up the new values. ECS reads secrets at task start, not continuously. 
    aws ecs update-service --cluster j9-dev-cluster --service j9-dev-okr      --force-new-deployment
aws ecs update-service --cluster j9-dev-cluster --service j9-dev-dataroom --force-new-deployment
Never set J9_DEV_MOCK in AWS

The Data Room supports J9_DEV_MOCK=1 with J9_DEV_MOCK_ROLE=investor|admin as a local convenience so developers can work before a key exists. Per HANDOFF.md, it takes precedence over live mode.

If that variable ever reaches a deployed task definition, the app stops asking the platform anything and hands out whichever role the variable names — to everyone. Grep your task definitions for it before every prod deploy. Better: add a startup assertion in the app that refuses to boot when J9_DEV_MOCK is set and NODE_ENV=production, and raise it as a pull request.

NEXT_PUBLIC_ variables are baked at build time

NEXT_PUBLIC_PLATFORM_PORTAL_URL is inlined into the client bundle when next build runs, not read at container start. Setting it in the task definition does nothing for the browser code.

Two ways to handle it. Either pass it as a Docker build argument, which means one image per environment and breaks the promote-the-same-digest model — or change the app to read the value from a server component and pass it down as a prop, which keeps one image for both environments. The second is better and is a small code change worth raising. Until then, build-arg it and accept two images for the Data Room specifically.

The same applies to NEXT_PUBLIC_BASE_PATH, which next.config.ts sets from a constant — that one is fine, because it never differs between environments.

4.6 — IAM roles for the tasks

Two roles per service. The execution role is what ECS itself uses to pull the image, read secrets, and write logs before your code runs. The task role is what your code uses at runtime. Conflating them is a common shortcut that grants the application far more than it needs.

Ecosystem/infra/terraform/50-compute/iam-tasks.tf

locals {
  services = ["platform", "worker", "okr", "dataroom"]

  # The worker shares the platform's parameter scope; everything else owns its own.
  param_scope = {
    platform = "platform"
    worker   = "platform"
    okr      = "okr"
    dataroom = "dataroom"
  }
}

# ------------------------------------------------------------ execution roles
data "aws_iam_policy_document" "ecs_assume" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ecs-tasks.amazonaws.com"]
    }
  }
}

resource "aws_iam_role" "exec" {
  for_each           = toset(local.services)
  name               = "${local.prefix}-${each.key}-exec"
  assume_role_policy = data.aws_iam_policy_document.ecs_assume.json
}

resource "aws_iam_role_policy_attachment" "exec_managed" {
  for_each   = aws_iam_role.exec
  role       = each.value.name
  policy_arn = "arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy"
}

# The one addition: reading this service's own SSM parameters and decrypting them.
# Note the path is scoped to BOTH the environment and the service. A dev okr task
# cannot read /j9/prod/... and cannot read /j9/dev/dataroom/... either.
data "aws_iam_policy_document" "exec_secrets" {
  for_each = toset(local.services)

  statement {
    actions = ["ssm:GetParameters", "ssm:GetParameter", "ssm:GetParametersByPath"]
    resources = [
      "arn:aws:ssm:${var.region}:824999955649:parameter/j9/${local.env}/shared/*",
      "arn:aws:ssm:${var.region}:824999955649:parameter/j9/${local.env}/${local.param_scope[each.key]}/*",
    ]
  }

  statement {
    actions   = ["kms:Decrypt"]
    resources = [data.terraform_remote_state.secrets.outputs.kms_key_arn]
  }
}

resource "aws_iam_role_policy" "exec_secrets" {
  for_each = toset(local.services)
  name     = "read-own-parameters"
  role     = aws_iam_role.exec[each.key].id
  policy   = data.aws_iam_policy_document.exec_secrets[each.key].json
}

# ----------------------------------------------------------------- task roles
resource "aws_iam_role" "task" {

How to check the scoping actually holds

Use the IAM policy simulator, or just try it from inside a task once ECS Exec is on:

aws ecs execute-command --cluster j9-dev-cluster \
  --task <task-id> --container okr --interactive --command "/bin/sh"

# Inside the container:
aws ssm get-parameter --name /j9/dev/okr/J9_APP_API_KEY --with-decryption   # succeeds
aws ssm get-parameter --name /j9/dev/dataroom/J9_APP_API_KEY --with-decryption  # AccessDenied
aws ssm get-parameter --name /j9/prod/okr/J9_APP_API_KEY --with-decryption      # AccessDenied

The second and third commands failing is the whole point of putting two environments in one account safely. If either succeeds, stop and fix the policy before you put real data in prod.
