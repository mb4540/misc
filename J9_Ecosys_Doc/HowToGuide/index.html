Jemba9 Ecosystem — AWS Hosting Primer

Standing up dev and prod for the Jemba9 ecosystem

A working primer for a developer who has just been handed the Jemba9_Ecosystem repository and asked to make it run in AWS.

Covers the platform, the OKR app, and the Data Room app — one AWS account, two environments, Terraform throughout.

Read this page first

You are going to build two complete, isolated environments — dev and prod — inside a single AWS account, and deploy four long-running services into each of them. Everything is Terraform, everything deploys through GitHub Actions, and no human ever holds an AWS access key.

This guide is written to be executed top to bottom. The Terraform and Dockerfiles are complete enough to copy, but every one of them has at least one value you must confirm before apply. Those are called out where they appear.

The shape of it

Four things run continuously in each environment:

ServiceSourceServesPort
platformEcosystem/ login, the portal launcher, the Admin app, and the central can() authorization service 3000
workerEcosystem/, same image BullMQ jobs: grant-expiry sweep, health polling, event rollups, retention —
okrApplications/OKR/ the OKR + CFR app under /okr3001
dataroomApplications/dataroom/ the investor Data Room under /dataroom8080

Each app is an independent project with its own build, its own database, and its own deploy. They talk to the platform only over the network. That independence is the whole design, and it is what makes the infrastructure straightforward: three near-identical Fargate services behind one load balancer.

Ground rules this guide follows

One account, two environments

Account 824999955649 holds both. Separation is by Terraform workspace, name prefix, and a separate VPC per environment — not by account.

Region us-west-2

Matches company.config.yaml, which application code already reads. ACM certificates for CloudFront must additionally live in us-east-1.

ECS Fargate, not Amplify

Decided in docs/adr/0002-compute.md. The BullMQ worker is a second long-running process; Amplify and App Runner both fit it badly.

RDS PostgreSQL 16

The repo says Lakebase today, RDS as the target. Because the schema is standard PostgreSQL only, that move is a connection string plus a data copy.

No access keys, ever

Humans use IAM Identity Center SSO. CI assumes a role through GitHub OIDC. There is no aws_access_key_id anywhere in this design.

Fail closed

The apps deny everything when the platform is unreachable. That is deliberate, and it means network reachability between services is a correctness concern, not just an availability one.

Reading order

The eight chapters

  1. What you are hosting — the three deployables, what each needs at runtime, and the six application contracts that dictate infrastructure choices. Read this even if you want to skip ahead.
  2. Account foundation — SSO access, guardrails, the naming scheme, the Terraform layer layout, and the bootstrap layer that creates the state backend.
  3. Network and data — VPC across two AZs, the security-group chain, RDS, Redis, S3, and the SQL that creates three databases with an owner and a least-privilege runtime role each.
  4. Secrets and identity — KMS, SSM parameter naming, Cognito per environment, the app API keys, and the full environment-variable matrix for all four services.
  5. Compute — the code change you must make first, three Dockerfiles, ECR, task definitions, services, autoscaling, and the ALB with its path rules.
  6. The front door — ACM, WAF, CloudFront behaviors, the origin-verify secret, and the honest state of jemba9.com DNS.
  7. CI/CD — the GitHub OIDC trust policy, the deploy workflow, running migrations as a one-off task, and promoting an image digest from dev to prod.
  8. Runbook — local setup, the bootstrap checklist in order, smoke tests, a cost estimate, troubleshooting, the repo cleanup list, and the decisions still needing an owner.

Before you start: what you need

Access

  • An IAM Identity Center account assignment in 824999955649 through https://onej9.awsapps.com/start, with a permission set that can create IAM roles, VPCs, RDS, ECS, CloudFront, and WAF. In practice that is close to AdministratorAccess for the bootstrap and a narrower PowerUserAccess-plus-IAM set afterwards.
  • Write access to the GitHub repository holding Jemba9_Ecosystem, including the ability to create environments and environment secrets. (The repo still references CodeCommit in places; CodeCommit stopped accepting new customers in July 2024 and is not a target — see Ecosystem/docs/notes/deviation_codecommit.md.)
  • Knowledge of who controls the jemba9.com DNS zone and its registrar. This is a real, tracked blocker; see chapter 6. You can build and run everything without it.

amplify.yml is a leftover

amplify.yml at the repo root is an AWS Amplify Hosting build spec from an earlier attempt. It contradicts ADR 0002 (which chose Fargate) and it does something dangerous: it runs npx prisma migrate deploy inside the frontend build phase. Migrations belong in a separate, gated step. Delete the file, or leave it and never connect an Amplify app — but do not treat it as the plan.
