9. Configuration Management

Establishing and controlling product baselines through ECR/ECO change control, from requirements to as-delivered hardware

Student Introduction

Configuration Management (CM) answers a deceptively simple question: for any given unit of hardware, software, or documentation, do we know exactly what it is, what requirements it was built to, and what changed to get it there? For most companies that's a nice-to-have. For Jemba9, it's existential, because of how the Spacify™ process works.

Spacify takes a commercial baseline — a computer, controller, data router, power supply, robotic system, or sensor that was never designed for space — and adapts it into a space-qualified product. That adaptation only holds up if Jemba9 can prove, unit by unit, exactly which configuration was qualified and exactly which configuration shipped. If a supplier substitutes a component, a firmware revision slips in unnoticed, or a "minor" tweak on the shop floor isn't captured, the unit that flies may no longer be the unit that was qualified — and unlike a warranty return on a commercial product, that gap can mean a mission failure with no opportunity for a fix once the hardware is on orbit. Configuration drift is a direct mission-assurance risk for exactly the reasons Spacify makes Jemba9 fast: speed only stays safe if the baseline underneath it is rigorously controlled.

QP-002 defines four baselines that track a product through its life: the Functional Baseline (requirements, set at SRR), the Allocated Baseline (preliminary design, set at PDR), the Product Baseline (released drawings, BOMs, and firmware, set at CDR), and the Released Baseline (as-built, as-delivered, set at first article acceptance). Once a baseline is released, no change happens informally — it goes through an Engineering Change Request (ECR) to propose and assess the change, and, if approved, an Engineering Change Order (ECO) to actually authorize and document it, including how work-in-progress is dispositioned (incorporate, rework, or scrap). A deviation is a pre-delivery exception approved before the fact; a waiver is a post-manufacture acceptance of an as-built nonconformance, tied to an NCR. BOM revisions live in Cetec ERP, engineering drawings and source code live in version-controlled repositories, and firmware builds are tagged and hashed (SHA-256) specifically so that "what's actually in the box" can be verified rather than assumed — the same LEAN, evidence-over-assumption discipline that runs through the rest of the QMS.

Two audits close the loop before delivery: the Functional Configuration Audit (FCA) verifies the product performs to its requirements, and the Physical Configuration Audit (PCA) verifies the as-built unit matches the released drawings and BOM. Both feed the FAI Checklist (QF-009). This is where configuration management becomes the customer-facing proof that Spacify's speed didn't come at the cost of traceability.

Who needs this training: Engineering (Systems Engineers, Chief Engineer/design leads), Manufacturing Management, the Quality Manager, and Program Managers — anyone who originates, approves, or is affected by a change to a released design, drawing, BOM, or firmware baseline.

Syllabus & Training Goals

Class Syllabus

  1. Why configuration management is a mission-assurance issue at Jemba9 specifically — Spacify baselines and configuration drift risk
  2. The four configuration baselines: Functional (SRR), Allocated (PDR), Product (CDR), and Released (first article), their contents, owners, and change authority
  3. Configuration identification: part numbers, drawing numbers, semantic versioning for software/firmware, and the Configuration Item (CI) List
  4. Engineering Change Request (ECR): proposing a change, required fields, and the Engineering/Quality/Program Manager review chain
  5. Engineering Change Order (ECO): authorizing a change, incrementing revisions, and WIP disposition (incorporate / rework / scrap)
  6. Deviation vs. waiver: pre-delivery exception vs. post-manufacture acceptance, and their link to NCRs
  7. Software and firmware configuration control: version control, tagged releases, build manifests, and SHA-256 hashing of binaries
  8. Functional Configuration Audit (FCA) and Physical Configuration Audit (PCA), and their link to the FAI Checklist (QF-009)
  9. Records and retention: ECR/ECO/deviation/waiver records and CI Lists, life of program plus 10 years

Learning Objectives

By the end of this session, participants will be able to:

  • Name the four configuration baselines in order and the program milestone at which each is established
  • Distinguish an ECR from an ECO and state what each one authorizes
  • Distinguish a deviation from a waiver and identify which applies before vs. after manufacture
  • Explain how a WIP disposition decision (incorporate/rework/scrap) gets made on an approved ECO
  • Describe how firmware and software releases are tracked so the as-built configuration can be verified
  • Explain why configuration drift is a higher-consequence risk for Jemba9's Spacify-adapted hardware than for a typical commercial product

Recommended audience:

Engineering Chief Engineer / Design Leads Systems Engineers Manufacturing Management Quality Program Managers

Suggested periodicity: Onboarding for all Engineering, Manufacturing, and Quality staff who touch released baselines, plus a refresher at the start of each new program (when a fresh set of baselines is established) and whenever QP-002 is revised.
