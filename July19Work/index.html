Space Assurance Gateway — Staging CDK Stack + Deploy Pipeline — documents/plans/active/25-staging-cdk-stack-and-deploy-pipeline-execution.md

Decision confirmed: staging uses a separate, dedicated Lakebase instance (not a schema on the shared dev instance) — chosen for blast-radius isolation and a cleaner path toward commercialization. This requires no changes to already-approved CDK/backend code; it only affects the real credential values created below.
1. Provision a new Lakebase instance for staging
  1. Go to the sag-backend Databricks workspace: https://dbc-10400a1c-b271.cloud.databricks.com
  2. Left nav → Compute → Lakebase tab
  3. Click Create database / project — do not open the existing sag-dev project (that's dev's instance)
  4. Name it sag-staging so it's unambiguous in the console
  5. Wait for provisioning to finish, then open it → Overview → Roles & Databases tab (on the production branch overview page)
  6. Create (or note the auto-created) role — name it sag_backend_staging to avoid confusion with dev's sag_backend role
  7. Reset password on that role (⋮ menu → Reset password) — copy the generated password immediately, you won't see it again
  8. Note the host (e.g. ep-<something>.database.us-west-2.cloud.databricks.com) and database name (likely databricks_postgres)
  9. Assemble the connection string: 
    postgresql://sag_backend_staging:<password>@<host>/databricks_postgres?sslmode=require
2. Create the two staging secrets in AWS Secrets Manager

Requires AWS_PROFILE=jemba9-dev with Secrets Manager write access, region us-west-2:

aws sso login --profile jemba9-dev
export AWS_PROFILE=jemba9-dev
export AWS_REGION=us-west-2

aws secretsmanager create-secret \
  --name sag/staging/database-url \
  --secret-string "postgresql://sag_backend_staging:<password>@<host>/databricks_postgres?sslmode=require" \
  --region us-west-2

aws secretsmanager create-secret \
  --name sag/staging/client-secret \
  --secret-string "<staging Databricks SP OAuth client secret>" \
  --region us-west-2

Step 2a — client-secret value: decide whether staging reuses the same sag-backend service principal as dev (simpler) or gets its own dedicated SP (more isolated, matches the "separate instance" spirit). If reusing dev's SP, copy the existing secret value from sag/dev/client-secret-BkOQto. If creating a new SP, that's a Databricks Account Console step (Chad Fisher typically does this per the existing setup docs).

Capture the exact ARNs from the create-secret output (they include a random 6-character suffix, e.g. sag/staging/database-url-Ab12Cd). These exact suffixed ARNs are required for the final handoff step below.
3. Create IAM Identity Center groups
  1. AWS Console → IAM Identity Center → Groups → Create group, three groups:
    • sag-developers-staging — developers who can push feature branches and open PRs, but are denied direct push to main and denied overriding approval rules
    • sag-staging-deployers — can trigger/approve break-glass staging actions (routine deploys are automated on merge)
    • sag-production-approvers — Mike Berry + Chad Fisher, who approve the prod-promotion pipeline's manual gate
  2. Add users to each group
  3. Attach the existing deny policy to the developers group: Groups → sag-developers-staging → Permission sets → attach sag-developer-main-protection-staging (this managed policy already exists in AWS from Phase 5 — infra/lib/codecommit-governance-stack.ts created it, just never attached it)
4. Associate the CodeCommit approval-rule template

No CDK/CloudFormation resource exists for this (confirmed in Phase 5) — it's CLI-only:

aws codecommit create-approval-rule-template \
  --approval-rule-template-name "sag-main-2-approvals" \
  --approval-rule-template-content '{
    "Version": "2018-11-08",
    "DestinationReferences": ["refs/heads/main"],
    "Statements": [{
      "Type": "Approvers",
      "NumberOfApprovalsNeeded": 2,
      "ApprovalPoolMembers": [
        "arn:aws:sts::824999955649:assumed-role/<infra-pool-role>/*"
      ]
    }]
  }' \
  --region us-east-2

aws codecommit associate-approval-rule-template-with-repository \
  --approval-rule-template-name "sag-main-2-approvals" \
  --repository-name j9ccgit \
  --region us-east-2

Replace <infra-pool-role> with the actual IAM role ARN pattern for your infra/admin pool (this defines who can count as one of the 2 approvers).

Handoff: once you have the 2 exact secret ARNs (step 2) and confirmation the groups/approval-rule are in place (steps 3–4), hand them to Cascade to update infra/lib/stage-config.ts with the real ARNs and proceed with Phase 10's actual cdk deploy sequence.
