Part 2

Language Tour — Definition vs. Usage

Every example below uses TALARIA's own domain — the J9Avionics TIA Power Board, NASA-EEE-INST-002 Class B derating, a 550 km LEO mission profile — so the syntax lands against something familiar.

Which TALARIA? The illustrative values come from the mock UI's demo fixtures, but the field names in the mapping table at §2.4 track the real application's Drizzle schema (backend/src/db/schema.ts), since that is what any actual integration would target. Part 4 keeps the two strictly apart.

2.1 The one idea: def versus usage

If you learn one thing about SysML v2, learn this. Every element kind comes in two flavours, and the pattern is uniform across the entire language — parts, ports, actions, states, requirements, constraints, cases, all of them.

  • Definition (part def Capacitor) — the reusable blueprint. A kind of thing. It does not exist in any particular system; it is the catalogue entry.
  • Usage (part c24 : Capacitor) — that blueprint appearing in a context, with context-specific values. This is the thing on the board at reference designator C24.

In v1 you had Blocks, part properties, and instance specifications, related by rules that differed per diagram type. In v2 it is one rule, everywhere. That uniformity is what makes the textual notation tractable and the metamodel small.

2.2 Structure — parts, attributes, ports, interfaces

Structural decomposition is nested part usages. Ports are the declared interaction points; interfaces connect them. Note that everything below is one continuous, indentation-nested text file — there is no separate "block definition diagram" and "internal block diagram" to keep in sync.

// ---- Definitions (the catalogue) ----
package J9Avionics {

    import ISQ::*;                    // standard quantity library
    import SI::*;                     // standard unit library

    attribute def PartGrade :> String;
    port def PowerPort {
        attribute voltage : VoltageValue;
        attribute current : ElectricCurrentValue;
    }

    part def PowerBoard {
        attribute revision   : String;
        attribute partsCount : Integer;
        port vin  : PowerPort;
        port v5v  : PowerPort;
        port v3v3 : PowerPort;
    }

    part def Capacitor {
        attribute mpn             : String;
        attribute manufacturer    : String;
        attribute ratedVoltage    : VoltageValue;
        attribute appliedVoltage  : VoltageValue;
        attribute dielectric      : String;
        attribute grade           : PartGrade;
    }

    // ---- Usages (this board, this revision) ----
    part tiaPowerBoard : PowerBoard {
        revision   = "Rev C";
        partsCount = 69;

        part C24 : Capacitor {
            mpn            = "CGA5L1X7R1H106K160AE";
            manufacturer   = "TDK";
            ratedVoltage   = 50 [V];
            appliedVoltage = 48 [V];
            dielectric     = "X7R";
            grade          = "industrial";
        }

        part C28 : Capacitor {
            mpn            = "CGA3E3X7R1H105K080AB";
            ratedVoltage   = 50 [V];
            appliedVoltage = 12 [V];
        }
    }
}
Note the units. 50 [V] is not a string — it is a quantity value from the standard ISQ/SI libraries. Unit mismatches are a type error, not a review finding. For an assurance product this is not cosmetic.

2.3 Constraints and requirements — the part that changes your product

In v1 a requirement was prose plus a link. In v2 a requirement def is a specialised constraint def: it has a subject, typed parameters, a human-readable doc string, and one or more Boolean assertions. It reads like natural language and evaluates like code.

// EEE-003 from the TALARIA requirements table, made evaluable.
requirement def CeramicCapacitorVoltageDerating {
    doc /*
     * Ceramic capacitors shall be derated to 75% of rated voltage
     * at maximum operating temperature (NASA-EEE-INST-002, Class B,
     * Table 3-2).
     */

    subject cap : Capacitor;

    attribute deratingFactor : Real default 0.75;

    require constraint {
        cap.appliedVoltage <= cap.ratedVoltage * deratingFactor
    }
}

// Applied to the actual board. This is what a run evaluates.
requirement eee003_C24 : CeramicCapacitorVoltageDerating {
    subject cap = tiaPowerBoard.C24;   // 48 V > 37.5 V  => FAIL, severity 2
}
requirement eee003_C28 : CeramicCapacitorVoltageDerating {
    subject cap = tiaPowerBoard.C28;   // 12 V <= 37.5 V => PASS
}

Requirements compose. A mission-level requirement can be satisfied by a set of lower-level ones, and the satisfaction relationship is itself a model element — which means a traceability matrix is a query, not a spreadsheet somebody maintains.

requirement def MissionRadiationTolerance {
    doc /* All EEE parts shall tolerate min TID 30 krad(Si) with 2x RDM. */
    subject item : EeePart;
    attribute missionTid : Real;      // 30 krad from mission profile mp-001
    attribute rdm        : Real;      // 2.0
    require constraint { item.tidCapability >= missionTid * rdm }
}

satisfy requirement MissionRadiationTolerance by tiaPowerBoard;

2.5 Cases — analysis, verification, use

SysML v1 had use cases. v2 generalises the idea into three kinds, all sharing a common structure of subject, objective, parameters and returned result.

analysis def DeratingAnalysis {
    subject board : PowerBoard;
    in attribute standard : String;        // "NASA-EEE-INST-002"
    in attribute deratingClass : String;   // "Class B"
    in attribute mode : AnalysisMode;      // nominal | worstCase
    return attribute findings : Finding[0..*];
}

verification def VerifyVoltageDerating {
    subject cap : Capacitor;
    objective {
        verify requirement CeramicCapacitorVoltageDerating;
    }
    return verdict : VerdictKind;   // pass | fail | inconclusive | error
}

2.6 States — lifecycle phases as a first-class model

TALARIA's ten lifecycle phases with gate criteria are, in modelling terms, a state machine with guarded transitions. In v2 that is directly expressible, which means the gate logic stops living only in application code.

state def ProgramLifecycle {
    entry; then InitiateProgram;

    state InitiateProgram;
    state EstablishRequirements;
    state DefineArchitecture;
    state PreliminaryDesign;
    state DetailedDesign;
    // ... phases 6-10

    transition InitiateProgram then EstablishRequirements
        accept AdvancePhaseRequest
        if sowBaselineEstablished
        and rapdaPersonaConfigured
        and customerInterviewScheduled
        and teamRolesAssigned;
}

2.7 Metadata — how you add Jemba9-specific vocabulary

UML stereotypes are gone. Domain extension in v2 is a metadata def, which is a real semantic construct rather than a decoration. This is the mechanism you would use for maturity gating, export markings, waiver state, and counterfeit-risk flags.

metadata def CustomerVisibility {
    attribute maturityLevel : MaturityKind;   // L1..L4
    attribute releasedToCustomer : Boolean;
    attribute exportMarking : String;         // e.g. "ITAR"
}

metadata def WaiverRecord {
    attribute waiverId : String;
    attribute status : WaiverStatus;
    attribute justification : String;
    attribute approvedBy : String;
}

// Attach it. The finding for the FDS100 photodiode carries its waiver in-model.
part photodiode : EeePart {
    @WaiverRecord {
        waiverId      = "w-001";
        status        = "approved";
        justification = "No applicable EEE-INST-002 rule for commercial TO-5 Si PIN; "
                        "operates at <10% of absolute maximum ratings.";
    }
}
