Part 4

SysML 2.0 in the Context of TALARIA

Two artefacts, not one

This part reviews two distinct things, and keeps them separate throughout:

THE MOCK UI
_project-docs/mockups/active
Node + Express + EJS, 24 JSON files, one server process. A clickable specification artefact. Explicitly disposable.
THE REAL APPLICATION
j9ccgit/ monorepo
4 React 19 SPAs, Express + Drizzle backend over Postgres (48 tables), LangGraph.js agent pipeline, AWS CDK infra, Databricks. Under active development.

They are not the same maturity and they do not warrant the same recommendation. Where a statement applies to only one, it is labelled.

Headline finding

The real application has already converged on most of SysML v2's structure independently.

The Drizzle schema carries a three-level physical decomposition (board → assembly → part), typed numeric rated/actual/limit/margin columns, a data-driven rule table with provenance back to a document section, a stress-case table that is literally a constraint evaluation, a requirement-trace relationship table, and an agent-trace/evidence/approval chain. Those are, respectively, part usages, attributes, a constraint library, constraint assertions, satisfy/derive relationships, and provenance. Adopting SysML v2 here is a renaming and a formalisation, not a re-architecture. The gaps that remain are narrow and specific — see §4.4.

4.1 The mock UI — what it is and what it is for

Reviewed from _project-docs/mockups/active. A Node 20 + Express + EJS server on port 4000, no build step, backed by 24 JSON files acting as a mock database, driven by the FE-01 to FE-09 feature requirements. Its own SOLUTION.md is explicit that it exists to be a specification artefact for the production build, and to be thrown away afterwards. Six scripted flows demonstrate the Input → Agent Workflow → Output → Review loop.

Bearing on SysML v2: the mock is a UX specification, not a data specification. Its JSON is deliberately shallow — "50V" as a string, designators as a comma-separated list, rules baked into narration. Do not draw data-architecture conclusions from it, and do not target it for SysML work beyond a throwaway demo. The recommendations below are aimed at the real backend.

4.2 The real application — as built

4.3 What the real app already does right

Four of these are worth calling out, because each one materially shapes the SysML v2 recommendation that follows.

1 · Derating rules are already data, with provenance

The derating_rule table holds standard, version, componentType, parameter, deratingFactor, environment, rationale, effectiveDate, isActive, plus documentId and sectionCode pointing back into standard_document / document_section. New rules arrive through derating_rule_staging with an LLM confidence score and a human review gate before promotion. That is a versioned, auditable, provenance-linked rule library — the hard part of a SysML v2 constraint library is already done. What is missing is only the formal expression syntax and the ability to evaluate a rule symbolically rather than through hand-written TypeScript.

2 · The arithmetic is deterministic; only rule selection is LLM-mediated

In nodes/derating-analyst.ts, computeMargin() and determineStatus() are plain functions with unit tests. The LLM resolves which rule applies to a given component type; it does not compute the verdict. This is the right architecture and it is the reason a SysML v2 migration is tractable — you are replacing a rule-selection heuristic with typed specialisation, not replacing a language model's judgement with a solver.

3 · Decomposition and relationships exist as tables

board → assembly → part is a genuine containment hierarchy — a part usage tree in SysML terms. requirement_trace carries sourceReqId, targetReqId and a relationshipType, which is exactly the shape of derive / satisfy / refine. The decomposition and the traceability graph are both real structures, not conventions.

4 · Provenance is a chain, not a log

agent_trace (with parentTraceId, reasoningSummary, inputSummary/outputSummary, brickType) links to evidence (with sourceDocument, sourceUrl) and to approval (with reviewerRole, versionReviewed, decision). Every row carries createdBy/updatedBy/tenantId. An insurer-grade evidence trail is largely present; what it lacks is immutable snapshotting, which is precisely what the v2 API's commit model provides.

4.4 The real gaps

Set against what is already built, five gaps remain. These are the ones SysML v2 actually addresses.

Gap Evidence in the real codebase, and what v2 offers
No connectivity modelThere is no net, node, or port table. part.actualVoltage is an asserted number with no modelled source, so the platform cannot answer "what drives this node?" — the first question a reviewer asks about a 48 V stress on a 50 V part. v2 port def / connect supplies the missing layer and is the prerequisite for real ECAD netlist ingest (FE-08 currently stubs this).
Quantities are unitless doublesratedVoltage, actualPower, marginPercent are all doublePrecision with the unit implied by the column name. Better than the mock's strings, but a krad/rad or mW/W error is still a silent data bug rather than a type error. v2's ISQ/SI quantity libraries make it a parse failure.
Requirements are prose beside the rules, not above themThe requirement table holds title, description, status, tbxStatus — with no structural link to the derating_rule rows that would verify them. The verification relationship lives in the analyst's logic, not in data. v2 makes a requirement a specialised constraint, so status becomes computed.
No configuration baselineGrepping the schema, version appears only as per-row integers on deliverables and approvals. There is no table representing "the state of project P at gate 5". Rows mutate in place with updatedAt. FE-06 calls for configuration baselines; the v2 API's Commit/Branch/Tag model is a ready-made answer.
No variability modelboard.revision is a varchar. Rev C versus Rev D is a naming convention, not a structure, so "which requirements does Rev D put at risk?" cannot be computed. v2 variation/variant, or API branches, close this.

4.6 What a rule looks like in each form

The same NASA-EEE-INST-002 Class B ceramic-capacitor voltage rule, three ways. This is the clearest illustration of what changes and what does not.

// 1. REAL APP TODAY — a factor row, plus TypeScript that knows what to do with it.
//    derating_rule:
{ standard: "EEE-INST-002", version: "Rev C", componentType: "Capacitor, Ceramic",
  parameter: "voltage", deratingFactor: 0.75, environment: "Class B",
  documentId: "<uuid>", sectionCode: "3-2", isActive: true }

//    nodes/derating-analyst.ts:
export function computeMargin(deratedLimit: number, actualValue: number): number {
  if (deratedLimit === 0) return -100.0;
  return ((deratedLimit - actualValue) / deratedLimit) * 100.0;
}
//    ^ correct, tested, and completely opaque to any tool that is not TALARIA.

// 2. SysML v2 — the rule carries its own meaning.
requirement def CeramicCapacitorVoltageDerating {
    doc /* Ceramic capacitors shall be derated to 75% of rated voltage at
             maximum operating temperature. NASA-EEE-INST-002 Rev C, Table 3-2, Class B. */

    subject cap : CeramicCapacitor;
    attribute deratingFactor : Real default 0.75;
    attribute :>> sourceSection = "3-2";      // provenance travels with the rule

    require constraint {
        cap.appliedVoltage <= cap.ratedVoltage * deratingFactor
    }
}

// The margin computation is derivable from the constraint, not hand-written.
// Any conformant tool can evaluate this. computeMargin() stays as a fast path.
The delta is small and the leverage is large. You are not replacing the rule pipeline — the ingestion, staging, human review and provenance chain all stay. You are changing the representation of the promoted rule from a factor plus interpreter into a self-describing constraint. That is a serialiser and a schema addition, not a rewrite.

4.7 Five integration options

A — Export a .sysml view of a project

A serialiser that walks board → assembly → part, mission_profile, requirement and derating_finding and emits SysML v2 textual notation. One new route module alongside the existing 44. No schema change, no agent change.

Target the real backend, not the mock. The real schema already has the typed numerics and the hierarchy; the mock does not. Exporting from the mock would produce a demo that misrepresents what you can actually do. Do it against Drizzle and validate the output through the pilot parser.

B — Formalise the rule library

Add an expression column to derating_rule holding the SysML v2 constraint text, populated during staging promotion. The Standards Librarian keeps its RAG retrieval for narrative and rule discovery; the promoted artefact becomes a formal constraint rather than a bare factor. computeMargin() remains as the fast evaluation path, now with a checkable specification above it.

Why this is the high-value move: the ingestion-plus-review pipeline that produces these rules is the expensive thing Jemba9 has already built. Expressing its output in a standard formal language turns a private database into a portable, citable asset — and makes the assurance claim demonstrable to a third party rather than merely asserted.

C — Ingest customer models

Accept a v2 model as an alternative to the CSV/interview ingress: text upload, or a pull from a customer API endpoint at a named commit, populating board/assembly/part, mission profile and requirements. The existing bom-import route becomes one of two paths. This is also where ports and connections would first land, since a customer model will carry them.

Segment unlocked: primes and agencies who currently cannot use TALARIA without retyping an existing model into a spreadsheet.

D — Serve the API

Implement Projects, Commits, Branches, Elements and Queries over the existing Postgres store. This is where the missing configuration-baseline capability (FE-06) arrives for free: a gate passage becomes a tag, a BOM revision becomes a branch, and the agent_trace/evidence/approval chain gains the immutability it currently lacks.

Positioning: the stakeholder portal stops being a bespoke read-only SPA and becomes a scoped read against a tagged baseline. That is a much easier thing to explain to an insurer's technical reviewer, and a much easier thing to audit.

E — Go native

Make a v2 repository the system of record; the Drizzle tables become a read projection for query performance.

Do not start here. The backend is under active development with a working migration path and a deploy constitution; a foundational swap now would stall feature delivery for an uncertain return. A–D each stand alone, and each teaches you something you need before E is a sensible question.

4.8 A phased path

4.9 The RAPDA angle

TALARIA's differentiator is the LangGraph pipeline: Standards Librarian retrieves, Derating Analyst applies, Evidence Builder assembles, Exception Reviewer adjudicates, with interrupt() gates for employee and customer review. The architecture is sound — deterministic computation with LLM-mediated selection, checkpointed, traced.

What it lacks is a formal substrate for the agents to write into. Today a node's output is rows and prose. SysML v2 offers three properties that rows and prose do not:

  • Generatable. An LLM can author textual notation against a published grammar. The Plan Drafter and Customer Interview graphs already produce structured artefacts; targeting a standard model language rather than a bespoke JSON shape costs little and buys interoperability.
  • Checkable. Generated output passes or fails a parser and a constraint evaluation. That is a verification loop on agent output — the hardest problem in shipping agents into a regulated domain, and one the existing MLflow/evaluation harness could measure directly.
  • Attributable. Elements sit at a commit with an author. agent_trace already captures who did what; commits make the result immutable too, which is what an insurer's evidence trail actually requires.

Framed for a demo: "RAPDA doesn't summarise your engineering. It edits your model, and every edit is checked against a formal rule and recorded against a commit." The real application can nearly say that truthfully today — the rule provenance, the deterministic evaluation and the trace chain are all in place. What is missing is the standard representation that makes the claim verifiable by someone outside Jemba9.

4.10 What I would do next week

  1. Write the serialiser against Drizzle, not the mock JSON — one project, covering board/assembly/part with typed quantities, mission profile, requirements, and the findings from one completed run. Run the output through the pilot implementation's parser. The mapping decisions will take longer than the code.
  2. Take three derating_rule rows and hand-write their SysML v2 constraint def equivalents. Evaluate them over the same parts and confirm they reproduce what computeMargin() produced. That is the proof that the domain content survives formalisation.
  3. Model one project's lifecycle_phase.gateCriteria as guarded transitions and check the result against what the lifecycle route computes today.
  4. Stand up the reference API Services implementation locally, push the exported model as a commit, query it back. Two hours; it will tell you more about option D than any amount of reading.
  5. Prototype the UX of SysML import/export in the mock — that is what the mock is for — while the real work happens in the backend.
  6. Decide whether the formalised standards library is a Jemba9 product in its own right. Given that the ingestion, staging and human-review pipeline already exists and is the expensive part, this is the highest-leverage commercial question on the list.
