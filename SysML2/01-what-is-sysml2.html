Part 1

What SysML 2.0 Is, and Why It Exists

1.1 The problem v1 could not solve

SysML v1 shipped in 2007 as a profile of UML 2 — systems-engineering concepts expressed as stereotypes applied to software-modelling constructs. A «block» was a UML Class wearing a hat. That decision bought fast adoption and cost twenty years of friction:

  • Ambiguous semantics. Two tools could read the same model and disagree about what it meant. Interchange via XMI was notoriously lossy — in practice most teams treated tool migration as a rewrite.
  • Nine diagram types, no single model. The diagram was the artefact. Consistency between a BDD, an IBD and an activity diagram was a matter of engineering discipline, not language enforcement.
  • Requirements were text with an ID. A v1 «requirement» carried a string and a satisfy link. Nothing in the language could evaluate whether it was met.
  • No API. Getting model data into an analysis pipeline meant a vendor plugin, a scripted XMI parse, or a person reading a diagram and retyping numbers.
  • Graphical-only. You could not meaningfully diff a model, review it in a pull request, or generate it programmatically.

The v2 submission team's response was to stop extending UML and build a purpose-designed language with formal semantics underneath it.

1.2 The three-specification stack

"SysML v2" colloquially means three separate OMG specifications that ship together. Understanding which layer does what saves a lot of confusion later.

Read it bottom-up: KerML defines what a model means; SysML defines the systems-engineering words; the API defines how anything else gets at it.

1.3 Where the standard is, as of August 2026

Practical read: the language is stable enough to build against. The point-one revision (KerML 1.1 / SysML 2.1) is refinement, not redesign. What is still maturing is commercial tool depth and round-trip migration from v1 estates — see Part 3.

1.4 v1 versus v2, without the marketing

Dimension SysML v1 SysML v2
FoundationUML 2 profile (stereotypes)Own metamodel on KerML; no UML dependency
SemanticsInformal, tool-interpretedFormal, logic-grounded — models are machine-checkable
NotationGraphical only (9 diagram types)Textual and graphical over one abstract syntax
Core abstractionBlock; part property; ad-hoc instance specificationUniform definition / usage pattern across every element kind
RequirementsText + satisfy/derive linksSpecialised constraint with typed parameters — evaluable in CI
AnalysisParametric diagrams, weak tool supportFirst-class analysis case and verification case
VariantsProprietary pluginsNative variation / variant constructs
ExtensionUML stereotypes / profilesKerML metadata definitions — semantically sound domain languages
InterchangeXMI, lossy in practiceStandard REST API + JSON; textual source as a portable format
Version controlBinary/XMI blobs; merge is painfulText files diff in git; API has native branch/commit resources
LLM friendlinessEffectively nil — models are picturesHigh — a model is text with a published grammar
Why this last row matters to Jemba9

That final row is the one with strategic weight for an agent-based product. In v1, an AI agent could not meaningfully read or author a system model. In v2 it can — the model is text, the grammar is published, and the semantics are formal enough that generated output can be validated rather than merely plausible. TALARIA's LangGraph pipeline in the real application — Standards Librarian, Derating Analyst, Evidence Builder, Exception Reviewer, with human-in-the-loop interrupts — is structurally exactly the kind of consumer SysML v2 was designed to enable.

1.5 What v2 does not give you

  • A migration path that is free. There is no lossless v1→v2 conversion, because many v1 constructs were ambiguous. Expect curated re-modelling of anything you care about.
  • A methodology. SysML v2 is a language, not a process. It will not tell you what a phase gate is or when to run a derating analysis. That remains your IP.
  • Domain content. There are no built-in EEE parts libraries, radiation models, or NASA-EEE-INST-002 derating tables. You supply those as libraries and metadata.
  • Mature commercial parity with v1 workflows. As of 2026, tool support is real but uneven; several vendors gate v2 behind specific editions or newer product lines.
