Part 3

The API, the Digital Thread, and the Tool Landscape

The language gets the attention. The API is the part that changes what a platform like TALARIA can build.

3.1 What "Systems Modeling API & Services" actually specifies

It is a REST/HTTP platform-specific model over a model repository. Standard CRUD plus query, with git-like versioning baked into the resource model rather than bolted on. The key resources:

Resource What it is
ProjectA versioned model repository. The unit of access control.
CommitAn immutable change set against a project. Carries created-by and timestamp — an audit trail by construction.
Branch / TagNamed refs to a commit. A configuration baseline is a tag.
ElementAny model element at a given commit, serialised as JSON with its typed properties and relationships.
QueryA stored, executable selection over elements — the mechanism behind traceability matrices, coverage reports, and impact analysis.
RelationshipElements too — satisfy, verify, derive, allocate are all navigable and queryable.
The consequence worth internalising: "which requirements are affected by this BOM revision?" stops being a report somebody assembles and becomes a GET with a query parameter. Same for evidence trails, coverage gaps, and change impact.

3.2 Federated, not monolithic

The older digital-thread pitch was a single authoritative repository that every tool wrote into. That never survived contact with a real supply chain. The v2 API architecture points somewhere different: federated services that speak a common protocol, more like the web than like a mainframe.

3.4 The space-sector angle

Two things are converging that matter to a space assurance product specifically:

  • Digital engineering mandates are real. NASA has been formalising Digital Engineering and MBSE from headquarters through to field centres, and the DoD CTO published SysML v2 transition guidance in February 2026. The direction of travel for programme deliverables is model-based, not document-based.
  • Model-based mission assurance already exists as a discipline. NASA's NEPP work on Systems Engineering and Assurance Modeling (SEAM) is precisely the "assurance as a model, not a PDF" thesis. SysML v2's evaluable requirements and standard API make that thesis substantially easier to implement.

The gap — and this is the commercially interesting part — is that neither the standard nor the tools supply the domain content: derating tables, radiation design margins, screening levels, prohibited-materials rules, part grade heuristics. That remains proprietary. A vendor who holds curated space-assurance domain content and speaks the standard protocol occupies a defensible position.

3.6 Sharp edges

  • Edition and licensing traps. "Our tool supports SysML v2" often means a specific newer product line. Verify at the SKU level in any customer conversation.
  • v1 estates are not portable. Existing customer models will not convert cleanly. Plan for coexistence, not cutover.
  • API maturity varies. The reference implementation is a proof of concept. Commercial API conformance is uneven — test against the specific endpoint you intend to integrate with.
  • Skills gap. The definition/usage discipline and the textual notation are a genuine relearn for engineers fluent in v1 diagrams. Budget training time.
  • The spec is still moving at the point release. 2.1 Beta is in pilot. Pin your parser version.
