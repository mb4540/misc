package TalariaAssurance {

  import ProtoPDAvionics::TIAPowerBoard::**;

  // Constraints from the Jemba9 standards library,
  // with the clause they came from.
  requirement def CeramicCapacitorVoltageDerating {
      subject cap : CeramicCapacitor;
      attribute :>> source = "EEE-INST-002 Rev C, Tbl 3-2";
      require constraint {
          cap.appliedVoltage <= cap.ratedVoltage * 0.75
      }
  }

  // Verdicts against your part usages.
  verification v_C24 : VerifyVoltageDerating {
      subject = TIAPowerBoard.powerStage.C24;
      verdict = fail;                     // 48 V > 37.5 V
      @EvidenceRef { runId = "run-0042";
                     clause = "3-2"; }
  }

  verification v_C28 : VerifyVoltageDerating {
      subject = TIAPowerBoard.powerStage.C28;
      verdict = pass;
  }

Why this matters more than it looks. A customer with an existing MBSE estate currently cannot use an assurance platform without retyping their model into a spreadsheet. That is not a small friction — it is the reason a prime with a mature Cameo or Rhapsody practice will not evaluate the product at all. 2

Round trip

1
You publish a design
Your tool commits the board to your repository.
2
TALARIA reads it at that commit
No copy, no retyping, no drift — a pinned read.
3
Assurance runs
Constraints from the Jemba9 standards library evaluate against your usages.
4
Results publish back
Verdicts, evidence and waivers land as a commit on a branch you review.
5
Your authority reads the same model
Insurer or agency gets a scoped read at a tag — not a PDF someone assembled for them.

TALARIA as a Systems Modeling API endpoint 3

OMG API & Services 1.0

Your tools talk to TALARIA the same way they talk to any conformant model repository. No proprietary SDK, no export-import cycle.

# The project
GET  /projects/J9Avionics

# Named baselines — every gate passage tags one
GET  /projects/J9Avionics/tags
     → baseline/phase5-entry → 8f2c1ae
       baseline/phase4-entry → 3d7b902
       baseline/req-freeze   → a41e6c8

# The board at a baseline, immutable
GET  /projects/J9Avionics/commits/8f2c1ae/elements?type=PartUsage

# Which requirements does this revision put at risk?
POST /projects/J9Avionics/queries
     { "from": "8f2c1ae", "to": "c02f5b1",
       "select": "requirements affected by changed usages" }

# Scoped read for an insurer — one tag, read-only, L3+ only
GET  /projects/J9Avionics/commits/8f2c1ae/elements
     Authorization: Bearer <stakeholder token>

What this replaces

  • ✓
    The bespoke insurer portal. A scoped read against a tag, rather than a purpose-built read-only SPA.
  • ✓
    The CSV round trip. Customers with a model no longer flatten it to import it.
  • ✓
    "Which version was this?" Every artefact cites a commit.
  • ✓
    Custom integrations per customer. One protocol instead of one connector each.
The positioning shift. With an API endpoint, TALARIA stops being an application customers log into and becomes a service in their digital thread. That is a different conversation with a prime's tooling group — and a much easier one, because it asks them to adopt a standard rather than a vendor.

Publishing assurance back as commits
Verification verdicts, the constraints that produced them and the waivers that excuse them are written into the customer's own repository on a branch they review. The assurance argument lives next to the design it is about.
Today: results stay inside TALARIA. What the customer gets is a document, and their model knows nothing about it.
2
Import as a first-class ingress path
A SysML v2 model becomes an alternative to the CSV and interview path, carrying structure the spreadsheet cannot — nesting, ports, connections, typed quantities and the customer's own requirements.
Today: the bom-import route accepts CSV and the customer interview captures mission context. Both work well; neither can accept a model.
3
Systems Modeling API & Services 1.0
The third specification in the SysML v2 stack, alongside KerML and SysML itself: a REST/HTTP model with Projects, Commits, Branches, Tags, Elements and Queries. It is the piece that makes a federated digital thread practical rather than aspirational.
Today: the backend has 44 REST route modules over 48 Postgres tables — most of the substance the API describes, and none of the protocol. Implementing it is a shaping exercise over an existing store rather than new capability.
