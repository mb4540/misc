1
constraint def / requirement def — the standards library
A derating rule becomes a parameterised Boolean expression with its source clause attached. The Standards Librarian's job changes from "find the right factor" to "select and bind the right constraint" — and the resulting artefact is readable by anything that speaks the standard.
Today: derating_rule already holds the factor with provenance back to document_section, fed by a staging table with an LLM confidence score and a human promotion gate. That pipeline is the expensive part and it is already built. The rule it produces just is not self-describing.
2
Evaluation over every usage
One constraint written against the definition evaluates across all 142 usages automatically. The arithmetic stays deterministic — the language model selects and binds, it does not decide pass or fail.
Today: the same separation already holds. computeMargin() and determineStatus() are plain unit-tested functions; the LLM only resolves which rule applies. This is the reason the migration is tractable at all.
3
Mission profile as bound parameters
TID, RDM, thermal range and class are inputs to the constraints rather than values duplicated into each rule. Change the orbit and every dependent verdict is stale by construction, which is exactly what you want an assurance tool to know.
Today: mission_profile exists and is passed to the run, but the coupling between a profile change and the affected findings is not modelled — it is re-derived by re-running.
4
analysis case pinned to a commit
The run declares its subject, its inputs and its return type, and executes against an immutable snapshot of the model. Re-running it later on the same commit gives the same answer — which is what makes a result citable months afterwards.
Today: derating_run captures an inputSnapshot jsonb blob and the agent pipeline is checkpointed with real human-in-the-loop interrupt() gates. What is missing is immutability of the underlying entity rows, which mutate in place.
