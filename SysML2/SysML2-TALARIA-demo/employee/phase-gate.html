1
state def with guarded transition
The ten-phase lifecycle is a state machine, and gate criteria are transition guards. Expressing it in the model means the guard evaluates against the same data the rest of the assurance argument uses — the gate cannot say "verified" while the requirements page says otherwise.
Today: lifecycle_phase.gateCriteria is a jsonb array of labelled checkboxes, and the evaluation lives in the lifecycle route. Perfectly functional, but opaque to the customer and not connected to requirement status.
2
Tailorable process, without a code change
Aerospace customers tailor their gates. When the transition is a model element, a customer's tailoring is a model edit reviewed like any other, rather than a feature request against the platform.
Today: phases and criteria are seeded per project, so tailoring is possible — but it is data entry against a fixed schema, not an expressible process model.
3
variation / branches — revision impact as a diff
With Rev D as a branch off a tagged Rev C, "what does this revision break?" is a diff plus a re-evaluation, not an engineering study. The answer names requirements, not files.
Today: the mock shows per-line qty_old/delta integers and the real schema has board.revision as a varchar. Neither can compute requirement impact across revisions.
4
Commit and Tag from the API & Services spec
Baselines come from the standard's versioning model rather than being built. A gate passage tags a commit; an analysis cites one; a customer release points at one. Provenance stops depending on nobody having edited a row since.
Today: agent_trace, evidence and approval give a genuine audit chain with createdBy on every row — but the entities they describe are mutable, so a months-old approval cannot be replayed against what was actually approved.
