EEE-003 as a formal requirement 1

requirement def 
requirement def CeramicCapacitorVoltageDerating {

    // The human-readable statement stays. It is documentation on a
    // structure, not the whole of what the requirement is.
    doc /* EEE-003 — Ceramic capacitors shall be derated to 75% of rated
             voltage at maximum operating temperature (Class B). */

    subject cap : CeramicCapacitor;          // what it applies to

    attribute deratingFactor : Real default 0.75;
    attribute :>> source = "EEE-INST-002 Rev C, Table 3-2";

    require constraint {                     // what makes it true
        cap.appliedVoltage <= cap.ratedVoltage * deratingFactor
    }
}

// Traceability is declared, not documented separately.
requirement eee001 : DeratingStandardCompliance;
requirement eee003 : CeramicCapacitorVoltageDerating;

derive eee003 from eee001;
satisfy eee003 by tiaPowerBoard.powerStage;
A requirement is a specialised constraint. It has a subject, typed parameters, prose for humans and an assertion for machines. That is the whole difference between a requirement you read and a requirement you can check.

Click any purple marker above to jump here
1
requirement def — prose plus an assertion
In SysML v1 a requirement was text with an ID and a satisfy link; nothing in the language could evaluate it. In v2 it is a specialisation of constraint def with a declared subject and typed parameters, so the same element serves the reviewer reading it and the pipeline checking it.
Today: the requirement table holds title, description, status and tbxStatus. It sits beside the derating_rule table with no structural link between the two.
2
Verification status becomes computed
Because the requirement carries its own assertion and the model carries the values, status is derived on demand for a given commit. A BOM change makes dependent statuses stale automatically instead of quietly leaving them wrong.
Today: status and verification state are curated fields. They are accurate when someone remembers to update them after a run.
3
satisfy, derive, verify as model elements
Relationships are first-class, navigable and queryable. The traceability matrix is a traversal, so it cannot fall out of step with the design, and impact analysis ("what does this change break?") is the same traversal run backwards.
Today: requirement_trace already stores typed relationships between requirements — this part is genuinely in place. What it does not reach is the parts and the rules on the other side of the verification.
